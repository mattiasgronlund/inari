# Proofs of the portable backend

Machine-checked proofs, in [Rocq](https://rocq-prover.org) with the [Flocq](https://flocq.gitlabpages.inria.fr) library, that parts of [`src/simd/generic.rs`](../src/simd/generic.rs) round correctly, and that `abs`, `floor`, `ceil`, `max`, `min`, `mul_add`, `recip`, `round`, `round_ties_even`, `sign`, `sqr`, `sqrt`, `trunc`, `-x`, `x + y`, `x - y`, `x * y` and `x / y` of intervals and decorated intervals, built on it, return what IEEE 1788 asks of them, that `acos`, `acosh`, `asin`, `asinh`, `atan`, `atan2`, `atanh`, `cos`, `cosh`, `exp`, `exp10`, `exp2`, `ln`, `log10`, `log2`, `pow`, `powi`, `sin`, `sinh`, `tan` and `tanh` of intervals and decorated intervals, which compute their bounds with MPFR, return what IEEE 1788 asks of them if MPFR does what its manual says and its exponent range contains that of `f64`, that `mul_rev_to_pair` of intervals and decorated intervals returns what its doc comment says, that `cancel_minus` and `cancel_plus` of intervals and decorated intervals return what their doc comments say, which is what IEEE 1788 asks of them, that the conversions with which `FromStr` for intervals and decorated intervals rounds the bounds of an interval literal to `f64`s with MPFR return what IEEE 1788 asks of textToInterval, and the one that `interval_exact!` calls what its doc comment says, if MPFR does what its manual says and the bounds are what the grammar, which is not proved, can return, that the constants of `Interval` and `DecInterval` from `E` to `TAU` are the tightest intervals around their values, that every decorated interval that the library makes is `com` only if its interval is nonempty and bounded, and that every interval that the library's constructors make, or that these operations, `convex_hull` and `intersection` compute from such intervals, is `valid`, under the same condition on MPFR for the functions that call it.

## What is proved

`add_ru_correct` in [`AddRu.v`](theories/AddRu.v):

```coq
Theorem add_ru_correct : forall x y,
  Generic.add_ru x y =
    Some (Bplus mode_UP (fst x) (fst y), Bplus mode_UP (snd x) (snd y)).
```

For all inputs, both lanes of `add_ru` are IEEE 754 binary64 addition rounded toward +∞. This includes the sign of a zero result, overflow, the infinities and NaN. The specification `Bplus mode_UP` is Flocq's. With the modelling choices below, `Some` also means that `add_ru` does not panic.

It follows from the theorems for the two paths that `lanewise2` chooses between:

```coq
Theorem add1_ru_fast_correct : forall x y,
  snd (Generic.add1_ru_fast x y) = true ->
  fst (Generic.add1_ru_fast x y) = Bplus mode_UP x y.

Theorem add1_ru_slow_correct : forall x y,
  Generic.add1_ru_slow x y = Some (Bplus mode_UP x y).
```

`sub_ru_correct` and `sub1_ru_correct` in [`SubRu.v`](theories/SubRu.v) do the same for subtraction rounded toward +∞, Flocq's `Bminus mode_UP`:

```coq
Theorem sub_ru_correct : forall x y,
  Generic.sub_ru x y =
    Some (Bminus mode_UP (fst x) (fst y), Bminus mode_UP (snd x) (snd y)).

Theorem sub1_ru_correct : forall x y,
  Generic.sub1_ru x y = Some (Bminus mode_UP x y).
```

`sub_ru` and `sub1_ru` add `-y` with the functions above. Flocq defines `Bminus` by its own case analysis, and `Bminus_Bplus_Bopp` shows that it agrees with `Bplus` of `Bopp y`.

`mul_ru_correct` in [`MulRu.v`](theories/MulRu.v) does the same for multiplication rounded toward +∞, Flocq's `Bmult mode_UP`, both with an FMA and without one:

```coq
Theorem mul_ru_correct : forall has_fma x y,
  Generic.mul_ru has_fma x y =
    Some (Bmult mode_UP (fst x) (fst y), Bmult mode_UP (snd x) (snd y)).

Theorem mul1_ru_fast_correct : forall fma x y,
  snd (Generic.mul1_ru_fast fma x y) = true ->
  fst (Generic.mul1_ru_fast fma x y) = Bmult mode_UP x y.

Theorem mul1_ru_tiny_correct : forall fma x y,
  Generic.mul1_ru_tiny fma x y = Some (Bmult mode_UP x y).

Theorem mul1_ru_slow_correct : forall x y,
  Generic.mul1_ru_slow x y = Some (Bmult mode_UP x y).
```

`has_fma` is `HAS_FMA`, which depends on the target. With an FMA, `two_prod_err` computes the error of the product with `mul_add`, and without one with Dekker's TwoProduct. The fast path accepts `x` and `y` if either is zero or not finite, and otherwise only if `RN(x * y)` is at least `2^-968` in magnitude and finite, and without an FMA also below `2^1023`, with both factors below `2^996`. `lanewise2` sends the lanes that it rejects, whose `x` and `y` are finite and nonzero, to `mul1_ru_tiny`. For finite, nonzero `x` and `y` with `|RN(x * y)| < 2^-968`, `mul1_ru_tiny` returns `2^-1074` or -0 by the sign of `RN(x * y)` if that is zero, and otherwise scales `x` by `2^128`, rounds the scaled product upward on the fast path, which accepts it with either value of `FMA`, and rounds that divided by `2^128` upward. That is `x * y` rounded upward, as rounding upward twice through the scaled product is rounding upward once (`RU_scaled` in [`MulRuTiny.v`](theories/MulRuTiny.v)). The theorem also shows that the `debug_assert!` that the fast path accepts the scaled product never fails. Every other input goes to `mul1_ru_slow`, which multiplies the significands as integers and rounds the product with `round_up_exact`. `mul_ru_impl_correct` states the same for `mul_ru_impl::<FMA>`, which the differential tests call with both values of `FMA`.

`div_ru_correct` in [`DivRu.v`](theories/DivRu.v) does the same for division rounded toward +∞, Flocq's `Bdiv mode_UP`, including division by zero, both with an FMA and without one:

```coq
Theorem div_ru_correct : forall has_fma x y,
  Generic.div_ru has_fma x y =
    Some (Bdiv mode_UP (fst x) (fst y), Bdiv mode_UP (snd x) (snd y)).

Theorem div1_ru_fast_correct : forall fma x y,
  snd (Generic.div1_ru_fast fma x y) = true ->
  fst (Generic.div1_ru_fast fma x y) = Bdiv mode_UP x y.

Theorem div1_ru_slow_correct : forall x y,
  Generic.div1_ru_slow x y = Some (Bdiv mode_UP x y).
```

The fast path computes `q = RN(x / y)` and the remainder `r = x - q * y`, and steps `q` up if `r` is nonzero and has the sign of `y`, which is exactly when `q < x / y`. If `x` or `y` is zero or not finite, `q` is already the result. Otherwise the fast path is valid only if `q` is normal and `|x| >= 2^-967`, so that `r` is a float. Where it is valid, the code computes `r` exactly, with `mul_add`, or without an FMA with Dekker's TwoProduct and Sterbenz's lemma. The slow path divides the significands as integers and rounds the quotient with `round_up_exact`, with a nonzero remainder as the sticky bit. `div_ru_impl_correct` states the same for `div_ru_impl::<FMA>`.

`sqrt_rd_ru_correct` in [`SqrtRdRu.v`](theories/SqrtRdRu.v) does the same for the square root, rounded toward -∞ in the first lane and toward +∞ in the second, Flocq's `Bsqrt mode_DN` and `Bsqrt mode_UP`, both with an FMA and without one:

```coq
Theorem sqrt_rd_ru_correct : forall has_fma x,
  Generic.sqrt_rd_ru has_fma x = Some (Bsqrt mode_DN (fst x), Bsqrt mode_UP (snd x)).

Theorem sqrt1_rd_correct : forall has_fma x,
  Generic.sqrt1_rd has_fma x = Some (Bsqrt mode_DN x).

Theorem sqrt1_ru_correct : forall has_fma x,
  Generic.sqrt1_ru has_fma x = Some (Bsqrt mode_UP x).
```

`sqrt1_fast` computes `s = RN(√x)` and the remainder `r = x - s * s`. `sqrt1_rd_impl` steps `s` down if `r < 0`, and `sqrt1_ru_impl` steps it up if `r > 0`. `sqrt1_fast` accepts `x` if `-966 <= exponent(x) <= 1023`, or `<= 1021` without an FMA. For a positive `x`, `r` is then a float, and the code computes it exactly, as for division. For a negative `x`, `s`, `r` and the result are NaN. `sqrt1_slow` scales any other positive finite `x` into that range by `2^128` or `2^-128`, and the rounded square root of the scaled input back by `2^-64` or `2^64`, all exactly. For ±0, ±∞, NaN and the other negative numbers, it returns `x.sqrt()`, which does not depend on the rounding mode. `sqrt1_rd_impl_correct` and `sqrt1_ru_impl_correct` state the same for `sqrt1_rd_impl::<FMA>` and `sqrt1_ru_impl::<FMA>` whenever their models may make a nested call through `sqrt1_slow`: one is always enough.

`mul_add_ru_correct` in [`MulAddRu.v`](theories/MulAddRu.v) does the same for the fused multiply-add rounded toward +∞, Flocq's `Bfma mode_UP`, both with an FMA and without one:

```coq
Theorem mul_add_ru_correct : forall has_fma x y z,
  Generic.mul_add_ru has_fma x y z =
    Some (Bfma mode_UP (fst x) (fst y) (fst z),
          Bfma mode_UP (snd x) (snd y) (snd z)).

Theorem mul_add1_ru_fast_correct : forall fma a b c,
  snd (Generic.mul_add1_ru_fast fma a b c) = true ->
  fst (Generic.mul_add1_ru_fast fma a b c) = Bfma mode_UP a b c.

Theorem mul_add1_ru_slow_correct : forall a b c,
  Generic.mul_add1_ru_slow a b c = Some (Bfma mode_UP a b c).
```

The fast path computes `r1 = RN(a * b + c)`, with `mul_add`, or without an FMA with `mul_add1_rn_emulated`, and the sign of its error with ErrFma [BM11] (see `generic.rs`), and steps `r1` up if the error is positive. If an input is not finite, or `a` or `b` is zero, both paths return `mul_add1_special(a, b, c)`, which computes `a * b + c` rounded to nearest, the same as toward +∞ for these inputs. Otherwise, if `c` is zero, the slow path rounds `a * b` with `mul1_ru_slow`. If not, it adds the exact product of the significands to `c` and rounds the sum with `sum_round_up`, as `add1_ru_slow` does for two floats. `lanewise2` takes only two arguments, so `mul_add_ru_impl` chooses between the paths itself, in the same way. `mul_add_ru_impl_correct` states the same for `mul_add_ru_impl::<FMA>`.

`floor_correct` in [`Integer.v`](theories/Integer.v) shows that `Interval::floor` returns the tightest interval that contains the image of its argument under `floor`, and `dec_floor_correct` that `DecInterval::floor` decorates it with the decoration that IEEE 1788 asks for:

```coq
Theorem floor_correct : forall x,
  valid x -> is_hull (image Rfloor x) (Interval.floor x).

Theorem dec_floor_correct : forall x, valid (itv x) ->
  if DecInterval.is_nai x then DecInterval.floor x = x
  else
    is_hull (image Rfloor (itv x)) (itv (DecInterval.floor x)) /\
    exists d, strongest d Rfloor (itv x) /\
      dec (DecInterval.floor x) = dec_min d (dec x).
```

`ceil_correct` and `dec_ceil_correct` state the same for `ceil`, with `Rceil`. `valid x` says that `x` is empty or `[a, b]` with `a <= b`, `a != +∞` and `b != -∞`, the bounds that `TryFrom<(f64, f64)>` accepts. `is_hull s y` says that the reals in `y` are exactly those between two elements of `s`, so no interval with `f64` bounds that contains `s` is smaller. `strongest d f x` says that the property of the decoration `d` holds for `f` on `x`, and that of no stronger decoration does. The result is decorated with the minimum of `d` and the decoration of `x`. A NaI is returned unchanged. The properties are those of IEEE 1788, with Stdlib's `continuity_pt` and `continue_in` for continuity, so where `floor` and `ceil` are continuous is proved, not assumed.

`Interval::floor` and `Interval::ceil` negate the first lane of `[-a; b]`, round both lanes in the same direction, and negate the first lane back. Section `Round` proves for any such rounding of floats that keeps ±∞ and NaN, is nondecreasing on the reals and moves a real by less than 1, that this gives the hull of the image, and that `impl_dec!` decorates it correctly if the decoration that it picks with `is_singleton` and its test `is_not_com` is the strongest one. `floor` is discontinuous exactly at the integers. If `floor(a) = floor(b)` for a bounded `[a, b]`, the restriction of `floor` to `[a, b]` is constant, and `floor` is continuous at each point of `[a, b]` unless `a` is an integer, which is the test `x.inf_raw() == y.inf_raw()`. For `ceil`, the test is on `b` instead.

`round_correct` and `dec_round_correct` in [`Round.v`](theories/Round.v) state the same for `round`, with `Rround`, and `round_ties_even_correct` and `dec_round_ties_even_correct` for `round_ties_even`, with `Rround_ties_even`. `trunc_correct` and `dec_trunc_correct` in [`Trunc.v`](theories/Trunc.v) state it for `trunc`, with `Rtrunc`. These are IEEE 1788's `roundTiesToAway`, `roundTiesToEven` and `trunc`, defined in [`Ieee1788.v`](theories/Ieee1788.v) with Flocq's `ZnearestA`, `ZnearestE` and `Ztrunc`.

`Interval::round`, `Interval::round_ties_even` and `Interval::trunc` round both lanes of `[-a; b]` as they are, without `neg0`. This gives the same result as negating the first lane, rounding it and negating it back, because the three roundings are odd on every float, signed zeros included: `round(-a) = -round(a)`. They also keep ±∞ and NaN, are nondecreasing on the reals and move a real by less than 1, so Section `Round` applies to them too.

`round` and `round_ties_even` are discontinuous exactly at the reals halfway between two integers, whichever way they break a tie. If `round(a) = round(b)` for a bounded `[a, b]`, the restriction of `round` to `[a, b]` is constant, and `round` is continuous at each point of `[a, b]` unless `a` or `b` is halfway between two integers. The test for that is `|a| - trunc(|a|) == 0.5`, and the same for `b`. Its subtraction is exact, as `trunc(|a|)` is 0 if `|a| < 1`, and otherwise between `|a| / 2` and `|a|`, so that Sterbenz's lemma applies (`is_half_test` in [`Nearest.v`](theories/Nearest.v)). The same holds for `round_ties_even`. `trunc` is discontinuous exactly at the nonzero integers. If `trunc(a) = trunc(b)` for a bounded `[a, b]`, `trunc` is continuous at each point of `[a, b]` unless `a` or `b` is a nonzero integer, which is the test `(x.inf_raw() != 0.0 && x.inf_raw() == y.inf_raw()) || (x.sup_raw() != 0.0 && x.sup_raw() == y.sup_raw())`.

`sign_correct` and `dec_sign_correct` in [`Sign.v`](theories/Sign.v) state the same for `sign`, with `Rsign`, which is -1 below 0, 0 at 0 and 1 above it, except that `dec_sign_correct` has one more hypothesis:

```coq
Theorem dec_sign_correct :
  forall x, valid (itv x) ->
  com_common x ->
  if DecInterval.is_nai x then DecInterval.sign x = x
  else
    is_hull (image Rsign (itv x)) (itv (DecInterval.sign x)) /\
    exists d, strongest d Rsign (itv x) /\
      dec (DecInterval.sign x) = dec_min d (dec x).
```

`Interval::sign` compares both lanes of `[-a; b]` with 0. It keeps `1.0` in the lanes above 0 and `-1.0` in those below, by `and`ing the constants with the masks of `gt` and `lt`, and combines the two with `or`, which leaves `0.0` in a lane that is neither. So each lane holds its own sign, `sign(-a) = -sign(a)` in the first and `sign(b)` in the second, and the result is `[sign(a), sign(b)]`. As `sign` is nondecreasing, that is the hull of the image. An infinite bound gives -1 or 1, which `sign` takes on the reals far enough out. `sign` is discontinuous exactly at 0. If `sign(a) = sign(b)` for a bounded `[a, b]`, the restriction of `sign` to `[a, b]` is constant, and `sign` is continuous at each point of `[a, b]` unless 0 is in it. With `sign(a) = sign(b)`, that is only `[0, 0]`, so the test is `x.inf_raw() == 0.0`.

The extra hypothesis, `com_common x`, says that `x` is `com` only if its interval is common, which every `DecInterval` that the library makes is (`ComCommon.v`, below). Unlike the roundings above, `sign` maps an unbounded interval on which it is constant, such as `[1, +∞]`, to a singleton, `[1, 1]`, for which `impl_dec!` picks `com`, where IEEE 1788 asks for `dac`, as `com` needs a bounded argument. Under the hypothesis, the decoration of `x` is not `com` there, and its minimum with `com` is the same as with `dac`.

`abs_correct` and `dec_abs_correct` in [`Abs.v`](theories/Abs.v) state the same for `abs`, with Stdlib's `Rabs`. `Interval::abs` matches on `classify`, which `transmute`s a `u8` into an `IntervalClass`. That is undefined behaviour unless the `u8` is the discriminant of a variant, and the model returns `None` then, so the theorems also state that the result is `Some`:

```coq
Theorem classify_defined :
  forall x, valid x -> exists c, Interval.classify x = Some c.

Theorem abs_correct :
  forall x, valid x ->
  exists y, Interval.abs x = Some y /\ is_hull (image Rabs x) y.
```

`classify` compares both lanes of `[-a; b]` with 0 by `ge` and `le`, and packs the four results into a code. Every comparison with NaN is false, so the empty interval gives 0, the code of `E`. Otherwise each lane is above, below or equal to 0. Of the nine combinations, six are the codes of the other variants, and the other three mean `a > b`, which `valid` rules out. `abs` returns `[a, b]` itself if `0 <= a`, the lanes swapped, `[-b, -a]`, if `a < 0` and `b <= 0`, and `[0, max(-a, b)]` if `a < 0 < b`, where neither lane is NaN or zero, so `max1` returns the larger. Each is the image of `[a, b]`. `abs` is continuous, and its result is bounded exactly when its argument is, so the strongest decoration is `trv` for the empty interval, `com` for a nonempty bounded one and `dac` for an unbounded one. `set_dec` returns `trv` for the empty interval, and otherwise keeps the decoration of the argument, except that it lowers `com` to `dac` for an unbounded result. That is the minimum of the strongest decoration and that of the argument in every case. So, unlike `dec_sign_correct`, `dec_abs_correct` has no extra hypothesis.

`max_correct` and `min_correct` in [`MaxMin.v`](theories/MaxMin.v) state the same for `max` and `min`, with Stdlib's `Rmax` and `Rmin`, and with `image2 f x y`, the image of the box `x × y` under `f`, in [`Ieee1788.v`](theories/Ieee1788.v):

```coq
Theorem max_correct :
  forall has_maximum x y, valid x -> valid y ->
  is_hull (image2 Rmax x y) (Interval.max has_maximum x y).
```

`has_maximum` is `HAS_MAXIMUM`, which depends on the backend. With `HAS_MAXIMUM` true, `Interval::max` of `[a, b]` and `[c, d]` takes `minimum` of the first lanes and `maximum` of the second, `[min(-a, -c); max(b, d)]`, which is `[max(a, c), max(b, d)]`. `Interval::min` takes `maximum` of the first lanes and `minimum` of the second. These return NaN in a lane where either argument is NaN, so an empty argument gives the empty interval, the hull of the empty image. Otherwise both lanes of each argument are finite or +∞, and on those `max1` and `min1` are `Rmax` and `Rmin`, with +∞ above every real. Two zeros give a zero of either sign, which is 0 either way. `max(r, t) <= s` exactly when `r <= s` and `t <= s`, and `s <= max(r, t)` exactly when `s <= r` or `s <= t`. So some point of the image is at most `s` exactly when `max(a, c) <= s`, and some point is at least `s` exactly when `s <= max(b, d)`, which makes `[max(a, c), max(b, d)]` the hull, and dually for `min`. An infinite bound needs no separate case. With `HAS_MAXIMUM` false, `Interval::max` and `Interval::min` return the empty interval if `either_empty`, and otherwise take `min` and `max` of the lanes where the other branch takes `minimum` and `maximum`. On lanes that are not NaN, `min1` and `max1` are `minimum1` and `maximum1`, so for valid arguments both branches return the same interval, lane for lane (`max_branches` and `min_branches` in `MaxMin.v`), and the theorems hold for either value.

`dec_max_correct` and `dec_min_correct` in [`DecMaxMin.v`](theories/DecMaxMin.v) state the decorations, with the extra hypothesis of `dec_sign_correct` for each argument:

```coq
Theorem dec_max_correct :
  forall has_maximum x y, valid (itv x) -> valid (itv y) ->
  com_common x ->
  com_common y ->
  if DecInterval.is_nai x then DecInterval.max has_maximum x y = x
  else if DecInterval.is_nai y then
    DecInterval.max has_maximum x y = DecInterval.NAI
  else
    is_hull (image2 Rmax (itv x) (itv y)) (itv (DecInterval.max has_maximum x y)) /\
    exists d,
      strongest2 d Rmax (itv x) (itv y) (itv (DecInterval.max has_maximum x y)) /\
      dec (DecInterval.max has_maximum x y) = dec_min d (dec_min (dec x) (dec y)).
```

A NaI first argument is returned unchanged, and a NaI second argument gives NaI. `strongest2` is `strongest` for a function of two reals, with the box `x × y` in place of `x` and continuity in R² in place of continuity in R. Its last argument is the computed interval, which `com` asks to be bounded (see "What is assumed"). The result is decorated with the minimum of `d` and the decorations of both arguments. `max` and `min` are continuous on R² and bounded on every bounded box, so the strongest decoration is `trv` if either argument is empty, `com` if both are nonempty and bounded, and `dac` otherwise. `set_dec_correct` in [`DecBinary.v`](theories/DecBinary.v) proves the rest once, for any function of two reals that is continuous on R², and for any result that is the tightest interval that contains the image (`is_tightest` below), as a hull is. It shows that `set_dec` of that result and the minimum `e` of the decorations of two `valid` arguments, neither of them NaI, keeps the result and decorates it with the minimum of `d` and `e`, if `e` is `com` only when a nonempty box with a bounded image is bounded. Section `Binary` in `DecMaxMin.v` applies it to any interval operation that returns the hull of the image, under the hypotheses of `dec_max_correct`.

The hypotheses are needed for the same reason as in `dec_sign_correct`: the hull of the image of an unbounded box can be common, as in `max([-∞, 1], [0, 2]) = [0, 2]`, and `set_dec` would keep `com` there if both arguments were `com`, where IEEE 1788 asks for `dac`.

`neg_correct` and `dec_neg_correct` in [`Neg.v`](theories/Neg.v) state the same as `floor_correct` and `dec_floor_correct` for `-x`, with Stdlib's `Ropp`. `Interval::neg` swaps the lanes of `[-a; b]` into `[b; -a]`, which stores `[-b, -a]`, the image of `[a, b]`, and computes nothing. Negation is continuous, and its result is bounded exactly when its argument is, so as for `abs`, `dec_neg_correct` has no extra hypothesis.

`add_correct` and `sub_correct` in [`AddSub.v`](theories/AddSub.v) show that `x + y` and `x - y` of intervals return the tightest interval that contains the image of the box `x × y` under Stdlib's `Rplus` and `Rminus`, and `dec_add_correct` and `dec_sub_correct` that the decorated versions decorate it as IEEE 1788 asks:

```coq
Theorem add_correct :
  forall x y, valid x -> valid y ->
  exists z, Interval.add x y = Some z /\ is_tightest (image2 Rplus x y) z.

Theorem dec_add_correct :
  forall x y, valid (itv x) -> valid (itv y) ->
  exists z, DecInterval.add x y = Some z /\
    if DecInterval.is_nai x || DecInterval.is_nai y then z = DecInterval.NAI
    else
      is_tightest (image2 Rplus (itv x) (itv y)) (itv z) /\
      exists d, strongest2 d Rplus (itv x) (itv y) (itv z) /\
        dec z = dec_min d (dec_min (dec x) (dec y)).
```

The image of `[a, b] × [c, d]` under `+` is `[a + c, b + d]`, whose bounds need not be floats, so the result is not its hull. `is_tightest s y` says that `y` is `valid`, contains `s`, and is contained in every `valid` interval that contains `s`. `Some` means that `add_ru` does not panic, as in `add_ru_correct`. `Interval::add` adds `[-a; b]` and `[-c; d]` with `add_ru`, which gives `[RU(-a - c); RU(b + d)]`. `add_lane` shows that `Bplus mode_UP` of two lanes that are finite or +∞ is the least float or +∞ at or above their sum: the sum rounded up if that does not overflow, +∞ if the sum overflows above, and `-f64::MAX` if it overflows below, as every float is at least `-f64::MAX`. A lane that is +∞ gives +∞. An empty argument gives NaN in both lanes, the empty interval. `Interval::sub` swaps the lanes of `y` first, so `x - y` is `x + (-y)`, and `sub_correct` follows from `add_correct` and `Neg.v`.

Unlike `max` and `min`, `+` and `-` need no hypothesis on the decorations of the arguments: if a nonempty box has a bounded image under `+`, the box is bounded, as `|r| <= |r + t| + |t|` for a `t` in `y`, and the same holds for `-`. But a sum can overflow where the image is bounded: `[f64::MAX, f64::MAX] + [f64::MAX, f64::MAX]` is `[f64::MAX, +∞]`, for which the strongest decoration is `dac`, as `com` asks for a bounded computed interval. This is why `strongest2` takes the computed interval.

`mul_correct` in [`Mul.v`](theories/Mul.v) shows that `x * y` of intervals returns the tightest interval that contains the image of the box `x × y` under Stdlib's `Rmult`, and `dec_mul_correct` that the decorated version decorates it as IEEE 1788 asks, with the extra hypothesis of `dec_max_correct` for each argument:

```coq
Theorem mul_correct :
  forall has_fma x y, valid x -> valid y ->
  exists z, Interval.mul has_fma x y = Some z /\ is_tightest (image2 Rmult x y) z.

Theorem dec_mul_correct :
  forall has_fma x y, valid (itv x) -> valid (itv y) ->
  com_common x ->
  com_common y ->
  exists z, DecInterval.mul has_fma x y = Some z /\
    if DecInterval.is_nai x || DecInterval.is_nai y then z = DecInterval.NAI
    else
      is_tightest (image2 Rmult (itv x) (itv y)) (itv z) /\
      exists d, strongest2 d Rmult (itv x) (itv y) (itv z) /\
        dec z = dec_min d (dec_min (dec x) (dec y)).
```

`has_fma` is the `HAS_FMA` that `mul_ru`, which `Interval::mul` calls, passes to `mul_ru_impl`, as in `mul_ru_correct`, and the theorems hold for both of its values. `Some` means that the `transmute`s in `classify` and `classify2` get the discriminant of a variant, and that `mul_ru` does not panic.

`Interval::mul` matches on `classify2`, which packs the classes of both arguments into one `u8` and `transmute`s it into an `IntervalClass2`, whose variant `X_Y` stands for the pair of classes `X` and `Y`. `classify2_pair` in [`Classify2.v`](theories/Classify2.v) shows that this gives the pair of the classes of the arguments whenever `classify` is defined on both, which `classify_defined` shows for `valid` intervals. The classes are `E`, the empty interval, `Z`, `[0, 0]`, `M`, `[a, b]` with `a < 0 < b`, `N0` and `N1`, with `a < b = 0` and `b < 0`, and `P0` and `P1`, with `0 = a < b` and `0 < a` (`classify_mem` in [`Classes.v`](theories/Classes.v)). `Interval::mul` takes the same branch for `N0` and `N1`, written `N` below, and for `P0` and `P1`, written `P`. `mul_correct` splits on the pair of classes and applies a lemma for each case: `mul_empty` and `mul_zero` in [`MulZero.v`](theories/MulZero.v) if a class is `E` or `Z`, `mul_MM` in [`MulMM.v`](theories/MulMM.v) if both are `M`, `mul_MN`, `mul_MP`, `mul_NM` and `mul_PM` in [`MulMRow.v`](theories/MulMRow.v) if one is, and `mul_NN`, `mul_NP`, `mul_PN` and `mul_PP` in [`MulNP.v`](theories/MulNP.v) if neither is. An empty argument gives the empty interval, as the image of a box with an empty side is empty. `[0, 0]` and a nonempty argument, in either order, give `Interval::zero()`, which holds `[+0; +0]`, i.e. `[0, 0]`, the tightest interval that contains the image `{0}`.

In the other cases, `tightest_lanes` in `AddSub.v` shows, as for `+`, that the result is the tightest interval if its second lane is the least float or +∞ at or above the largest product `r * t` of a real `r` of `x` and a real `t` of `y`, or +∞ if there is none, and its first lane the least at or above the largest negated product `-(r * t)`. `classify_lanes` in `Classes.v` shows what the class of a `valid` interval says about its lanes `[-a; b]`. [`MulTight.v`](theories/MulTight.v) shows which product of reals of two sets is the largest. [`MulLane.v`](theories/MulLane.v) shows that `Bmult mode_UP` of two lanes that are both finite, or both above 0, is the least float or +∞ at or above their product (`mul_lane_finite`, `mul_lane_pos`), where +∞ times a lane above 0 is +∞, and that `max1` of two such results is the least at or above the larger product (`max_least_lane`). `mul_ru` computes `Bmult mode_UP` in each lane (`mul_ru_correct`).

- `M × M`: the reals of each argument have both signs. The largest product is the larger of `(-a) * (-c)` and `b * d`, and the largest negated product the larger of `(-a) * d` and `b * (-c)` (`tight_mult_mixed`), all four products of two lanes above 0. `Interval::mul` computes the four with `mul_ru`, and takes `max` of the two in each lane.
- `M × N`, `M × P`, `N × M` and `P × M`: as `-(r * t) = (-r) * t = r * (-t)` and `r * t = (-r) * (-t)`, the largest product and the largest negated product are each the largest product of reals or negated reals of `x` and `y`, picked so that the factor from the argument in `N` or `P` is at least 0. That is the product of two lanes above 0 (`tight_mult_pos_r`, `tight_mult_pos_l`), which `Interval::mul` picks with `swap`, `shuffle02` and `shuffle13`.
- `N × N`, `N × P`, `P × N` and `P × P`: the reals of each argument have one sign, so `r * t` is `p * q` or `-(p * q)`, where `p` and `q` are the reals of `x` and `y`, or their negations, whichever are at least 0 (`image2_mult_opp_l`, `image2_mult_opp_r` and `image2_mult_opp_lr`). The largest `p * q` is the product of two lanes above 0 (`tight_mult_pos_r`). The largest `-(p * q)` is `-(m * n)` for the least `p` and `q`, `m` and `n` (`tight_mult_min`), which two finite lanes hold as `-m` and `-n`. `Interval::mul` negates one of them with `neg0`, so that their product is `-(m * n)`.

`Rmult_continuous` in `Mul.v` shows that `*` is continuous on R², so `set_dec_correct` in `DecBinary.v` gives the decorations if `e` is `com` only when a nonempty box with a bounded image is bounded. For `+` this holds whatever `e` is, but not for `*`: `[0, 0] × [1, +∞]` has the bounded image `{0}`. `[0, 0] * [1, +∞]` is `[0, 0]`, and `set_dec` would keep `com` there if both arguments were `com`, where IEEE 1788 asks for `dac`, as `com` needs a bounded box. So `dec_mul_correct` has the extra hypothesis of `dec_max_correct`, under which `[1, +∞]` is not `com`.

[`ComCommon.v`](theories/ComCommon.v) shows that this hypothesis of `dec_sign_correct`, `dec_max_correct`, `dec_min_correct` and `dec_mul_correct`, and of `dec_mul_add_correct`, `dec_recip_correct` and `dec_div_correct` below, holds for every `DecInterval` that the library makes:

```coq
Definition com_common (x : DecInterval) : Prop :=
  dec x = Com -> Interval.is_common_interval (itv x) = true.
```

It proves `com_common` for each place that makes a `DecInterval`. The fields of `DecInterval` are `pub(crate)`, so only the library can make one with a struct expression, and the only such expression is the body of `new_unchecked`. The only `transmute` into a `DecInterval` is the one in `const_dec_interval!`, and no code assigns to a field. Anything else that returns a `DecInterval` returns one that it was given, or one made by these. The callers of `new_unchecked` are:

- `DecInterval::new`, which picks `com` only for a common interval (`new_com_common`).
- `set_dec`, which keeps `com` only for a common interval and lowers it to `dac` otherwise (`set_dec_com_common`). The theorem holds for any interval and decoration, so it covers every caller, such as `x * y`.
- The constants `EMPTY`, `NAI` and `ENTIRE`, which are `trv`, `ill` and `dac` (`constants_com_common`), and those that `def_com!` decorates `com`, whose bounds are finite (`def_com_com_common`), as an assertion in `def_com!` checks at compile time (`def_com_ok_bounds`).
- `convex_hull` and `intersection`, which return NaI or a `trv` interval (`set_op_com_common`).
- `try_from_be_bytes`, `try_from_le_bytes` and `try_from_ne_bytes`, which accept `com` only for bounds `a <= b` where `a` is not -∞ and `b` is not +∞ (`try_from_bytes_com_common`). `a <= b` excludes NaN, and then `a` = +∞ would force `b` = +∞, and `b` = -∞ would force `a` = -∞, so both bounds are finite.

`const_dec_interval!(a, b)` picks `com` only if `a` is not -∞ and `b` is not +∞, and does not compile unless `a <= b`, which makes both bounds finite too (`const_dec_interval_com_common`).

`mul_add_correct` in [`MulAdd.v`](theories/MulAdd.v) shows that `Interval::mul_add`, IEEE 1788's `fma`, returns the tightest interval that contains the image of the box `x × y × z` under `Rfma`, `r * t + u`, and `dec_mul_add_correct` that `DecInterval::mul_add` decorates it as IEEE 1788 asks, with the hypothesis `com_common` for `x` and `y`, but not for `z`:

```coq
Theorem mul_add_correct :
  forall has_fma x y z, valid x -> valid y -> valid z ->
  exists w, Interval.mul_add has_fma x y z = Some w /\ is_tightest (image3 Rfma x y z) w.

Theorem dec_mul_add_correct :
  forall has_fma x y z, valid (itv x) -> valid (itv y) -> valid (itv z) ->
  com_common x ->
  com_common y ->
  exists w, DecInterval.mul_add has_fma x y z = Some w /\
    if DecInterval.is_nai x || DecInterval.is_nai y || DecInterval.is_nai z
    then w = DecInterval.NAI
    else
      is_tightest (image3 Rfma (itv x) (itv y) (itv z)) (itv w) /\
      exists d, strongest3 d Rfma (itv x) (itv y) (itv z) (itv w) /\
        dec w = dec_min d (dec_min (dec x) (dec_min (dec y) (dec z))).
```

`x` is `self`, `y` is `rhs` and `z` is `addend`. `image3` and `strongest3` in `Ieee1788.v` are `image2` and `strongest2` for a function of three reals, with the box `x × y × z` in place of `x × y` and continuity in R³ in place of continuity in R². The result is decorated with the minimum of `d` and the decorations of the three arguments, as `self.d.min(rhs.d.min(addend.d))` computes it. `has_fma` is the `HAS_FMA` that `mul_add_ru`, which `Interval::mul_add` calls, passes to `mul_add_ru_impl`, as in `mul_add_ru_correct`, and the theorems hold for both of its values. `Some` means that the `transmute`s in `classify` and `classify2` get the discriminant of a variant, and that `mul_add_ru` does not panic.

`Interval::mul_add` returns the empty interval if `z` is empty, before it classifies `x` and `y` (`mul_add_addend_empty` in [`MulAddZero.v`](theories/MulAddZero.v)). Otherwise it matches on `classify2`, as `Interval::mul` does, and in each case calls `mul_add_ru` on the same pairs of lanes that `Interval::mul` passes to `mul_ru`, with the lanes of `z` as the third argument. `mul_add_correct` splits on the pairs of classes as `mul_correct` does, with a lemma for each case: `mul_add_empty` in `MulAddZero.v` if `x` or `y` is empty, as the image of a box with an empty side is empty, `mul_add_zero` if one of them is `[0, 0]` and the other is nonempty, `mul_add_MM` in [`MulAddMM.v`](theories/MulAddMM.v) if both are `M`, `mul_add_MN`, `mul_add_MP`, `mul_add_NM` and `mul_add_PM` in [`MulAddMRow.v`](theories/MulAddMRow.v) if one is, and `mul_add_NN`, `mul_add_NP`, `mul_add_PN` and `mul_add_PP` in [`MulAddNP.v`](theories/MulAddNP.v) if neither is. Where one of them is `[0, 0]` and the other is nonempty, `Interval::mul_add` returns `z` itself: every product is 0, so the image is the set of reals of `z`, and a `valid` interval is the tightest interval that contains its reals (`tightest_self`).

In the other cases, the image is the set of sums `p + u` of a product `p` of a real of `x` and a real of `y` and a real `u` of `z` (`image3_fma` in [`MulAddLane.v`](theories/MulAddLane.v)). For a nonempty `z = [e, f]`, stored as `[-e; f]`, its largest element is the largest product plus `f`, and its largest negated element the largest negated product plus `-e`, and there is none if either term has none. `tightest_mul_add` in `MulAddLane.v` shows, with `tightest_lanes`, that the result is the tightest interval if its lanes are the least floats or +∞ at or above these, where the largest products are those of `x * y` (`MulTight.v`). `fma_lane_finite` and `fma_lane_pos` show that `Bfma mode_UP` of two lanes that are both finite, or both above 0, and a lane that is finite or +∞ is the least float or +∞ at or above the product of the first two plus the bound that the third stands for, as `mul_lane_finite` and `mul_lane_pos` do for the product alone. In `M × M`, adding the bound to the larger of two products is adding it to both and taking the larger (`uplus_umax`), so `max_least_lane` applies as in `x * y`. `mul_add_ru` computes `Bfma mode_UP` in each lane (`mul_add_ru_correct`).

No lane gives NaN. The lanes `-e` and `f` of a nonempty `valid` `z` are finite or +∞, and `Interval::mul_add` multiplies the same pairs of lanes as `Interval::mul`, two finite lanes or two lanes above 0, never 0 and ∞. So no lane computes `0 * ∞` or `∞ - ∞`: if a factor is +∞, the other is above 0, so the product is +∞, and as the lane of `z` is not -∞, the result is +∞. If the factors are finite and the lane of `z` is +∞, the result is +∞ too.

`Rfma_continuous` in `MulAdd.v` shows that `Rfma` is continuous on R³. `set_dec_correct3` in [`DecTernary.v`](theories/DecTernary.v) is `set_dec_correct` for a function of three reals, with the same argument, so it gives the decorations if `e`, the minimum of the decorations of `x`, `y` and `z`, is `com` only when a nonempty box with a bounded image is bounded. As for `x * y`, a box with an unbounded `x` or `y` can have a bounded image: `[0, 0] × [1, +∞] × [1, 2]` has the image `[1, 2]`, and `set_dec` would keep `com` there if all three arguments were `com`, where IEEE 1788 asks for `dac`. So `dec_mul_add_correct` has the `com_common` hypothesis for `x` and `y`. It needs none for `z`: if `x` and `y` are nonempty and the image is bounded, so is `z`, as `|u| <= |r * t + u| + |r * t|` for an `r` in `x` and a `t` in `y` (`fma_addend_bounded`).

`sqrt_correct` in [`Sqrt.v`](theories/Sqrt.v) shows that `Interval::sqrt` returns the tightest interval that contains the image of its argument under the square root, which is defined only on `[0, +∞)`, and `dec_sqrt_correct` that `DecInterval::sqrt` decorates it as IEEE 1788 asks:

```coq
Theorem sqrt_correct :
  forall has_fma x, valid x ->
  exists y, Interval.sqrt has_fma x = Some y /\
    is_tightest (image_dom sqrt_dom sqrt x) y.

Theorem dec_sqrt_correct :
  forall has_fma x, valid (itv x) ->
  exists y, DecInterval.sqrt has_fma x = Some y /\
    if DecInterval.is_nai x then y = x
    else
      is_tightest (image_dom sqrt_dom sqrt (itv x)) (itv y) /\
      exists d, strongest_dom sqrt_dom d sqrt (itv x) (itv y) /\
        dec y = dec_min d (dec x).
```

`sqrt_dom` is the domain `[0, +∞)`, and `image_dom sqrt_dom sqrt x` the image of the reals of `x` in it under Stdlib's `sqrt`, so the image of `[-1, 1]` is `[0, 1]`. Stdlib's `sqrt` returns 0 below 0, but those values are not used. `strongest_dom` is `strongest` for a function with a domain, and takes the computed interval, as `strongest2` does. `has_fma` is the `HAS_FMA` that `sqrt1_ru` and `sqrt_rd_ru` pass to `sqrt1_ru_impl` and `sqrt1_rd_impl`, and the theorems hold for both of its values. `Some` means that `sqrt1_ru` and `sqrt_rd_ru` return, as in `sqrt_rd_ru_correct`.

The image of a nonempty `[a, b]` is empty if `b < 0`, and otherwise holds the reals between `√max(a, 0)` and `√b`, with no upper bound if `b` is +∞ (`sqrt_image`). As for `+`, those bounds need not be floats, so the result is the tightest interval rather than the hull, and `tightest_lanes` in `AddSub.v` reduces it to the lanes. `Interval::sqrt` returns the empty interval if `x` is empty or `b < 0`. Otherwise, if `a <= 0`, it stores `[-0; sqrt1_ru(b)]`, i.e. `[0, sqrt1_ru(b)]`, and if `a > 0`, `neg0` turns `[-a; b]` into `[a; b]`, `sqrt_rd_ru` takes the square root of the first lane rounded down and of the second rounded up, and `neg0` turns the result back. These are Flocq's `Bsqrt mode_DN` and `Bsqrt mode_UP` (`sqrt1_ru_correct`, `sqrt_rd_ru_correct`). The square root of a finite float at least 0 is below `2^512`, so it stays finite when rounded up or down. So the second lane is `√b` rounded up, or +∞ if `b` is, the least float or +∞ at or above `√b`, and the first lane, `-0` or `-RD(√a)`, is the least float at or above `-√max(a, 0)`.

IEEE 1788 counts `sqrt` as continuous at each point of its domain, 0 included, so continuity is relative to the domain. The strongest decoration is `trv` if `x` is empty or has a real below 0, which, for a nonempty `x`, is when `a < 0`, `com` if `0 <= a` and `b` is finite, and `dac` if `0 <= a` and `b` is +∞, as `com` needs a bounded `x`. `DecInterval::sqrt` passes `trv` to `set_dec` if `a < 0`, and the decoration of `x` otherwise. `set_dec` returns the empty interval, decorated `trv`, for an empty result. Otherwise it keeps the decoration that it gets, except that it lowers `com` to `dac` for a result that is not common, which, if `0 <= a`, is when `b` is +∞. In each case, that is the minimum of the strongest decoration and that of `x`. So, unlike `dec_mul_correct`, `dec_sqrt_correct` has no `com_common` hypothesis: where `set_dec` gets the decoration of a nonempty `x`, the result is common exactly when `x` is bounded.

Stdlib's `Rinv` and `Rdiv` return 0 for a divisor 0, but those values are not used. `has_fma` is the `HAS_FMA` that `div_ru`, which `Interval::recip` and `Interval::div` call, passes to `div_ru_impl`, as in `div_ru_correct`, and the theorems hold for both of its values. `Some` means that the `transmute`s in `classify` and `classify2` get the discriminant of a variant, and that `div_ru` does not panic.

Unlike a set of products, a set of quotients of reals of two intervals need not have a largest or a least element: `recip([-∞, -1])` is `[-1, 0)`, whose least upper bound 0 is not in it, and `[1, 2] / [1, +∞]` is `(0, 2]`, whose greatest lower bound 0 is not in it. So the lanes of the result hold least upper bounds. `tightest_lanes_lub` in [`DivTight.v`](theories/DivTight.v) is `tightest_lanes` with `lub`, the least upper bound of a set or none if the set has no upper bound, in place of `tight`: the result is the tightest interval if its second lane is the least float or +∞ at or above the least upper bound of the image, and its first lane the least at or above that of the negated image (`lane_ok`).

`Interval::div` matches on `classify2`, as `Interval::mul` does, and `div_correct` splits on the 49 pairs of classes:

- The 19 pairs with an empty argument, or with `y` in `Z`, give the empty interval (`div_empty` in [`DivZero.v`](theories/DivZero.v)). The only real of `[0, 0]` is outside the domain of the divisor, so the image is empty.
- The 5 pairs with `x` in `Z` and `y` in `M`, `N0`, `N1`, `P0` or `P1` give `Interval::zero()` (`div_zero`), as such a `y` has a real `t` other than 0, and `0 / t = 0`.
- The 7 pairs `M × M`, `M × N0`, `M × P0`, `N0 × M`, `N1 × M`, `P0 × M` and `P1 × M` give `ENTIRE` (`div_entire`). In each, either `x` has reals of both signs and `y` has reals other than 0 as close to 0 as asked on one side of 0, or `x` has a real other than 0 and `y` such reals on both sides. So the image has no upper and no lower bound, and `ENTIRE` is the tightest interval that contains it (`tightest_entire`).
- The other 18 pairs call the ten helpers from `div_m_n1` to `div_p_p1` in `src/basic.rs`, and the lemmas from `div_MN1` to `div_PP1` in [`DivCases.v`](theories/DivCases.v) prove them, one per helper. `Interval::div` takes the same branch for `N0` and `N1` on the left, written `N`, and for `P0` and `P1`, written `P`.

`Interval::recip` matches on `classify`. `E` and `Z` give the empty interval and `M` gives `ENTIRE`, as for `/` (`recip_empty` and `recip_entire` in `DivZero.v`), and `recip_N0`, `recip_N1`, `recip_P0` and `recip_P1` in `DivCases.v` prove the other four classes.

In the cases that `DivCases.v` proves, the reals of the divisor are all at least 0 or all at most 0, and [`DivSets.v`](theories/DivSets.v) writes the image and the negated image as sets of quotients `quot U Q`, of a numerator in a set `U` and a denominator in a set `Q` of reals above 0. If the reals of `y` are at least 0, the numerators are the reals of `x` for the image and their negations for the negated image, as `-(r / t) = (-r) / t`, and the denominators are the reals of `y` other than 0. If they are at most 0, `r / t = (-r) / (-t)` swaps the two sets of numerators, and the denominators are the negations of the reals of `y` other than 0 (`div_image_P` and `div_image_N`). For `recip`, the numerators are `{1}` and `{-1}` (`recip_image_P` and `recip_image_N`). `DivTight.v` gives the least upper bound of `quot U Q` in three forms, and [`DivLane.v`](theories/DivLane.v) shows that the lane that `Interval::div` or `Interval::recip` computes for it is the least float or +∞ at or above it:

- (a) `U` has an element above 0 and a largest element `m`, or no upper bound, and `Q` has a least element `n`: the largest quotient is `m / n`, or there is none (`quot_tight_a`). The lane is `Bdiv mode_UP` of a lane above 0 and a float above 0, where +∞ divided by such a float is +∞ (`div_lane_pos`), or of their negations, which gives the same quotient (`div_lane_neg`).
- (b) `U` has an element above 0, and `Q` has elements as close to 0 as asked: the quotients have no upper bound (`quot_unbounded`), and the lane is +∞ (`div_lane_inf`).
- (c) `U` has a largest element `m <= 0`, and `Q` has a largest element `v` or no upper bound: the least upper bound is `m / v`, or 0 if `Q` has no upper bound (`quot_lub_c`). It is not in the set if `m < 0` and `Q` has no upper bound. The lane is `Bdiv mode_UP` of a float at most 0 and a lane above 0, where a float divided by +∞ is a zero, whose value is 0 (`div_lane_nonpos`).

What the class of each argument says about these sets is in `DivSets.v` (`xset_M`, `xset_N`, `xset_P`, `yset_P1`, `yset_P0`, `yset_N1` and `yset_N0`), and the header of `DivCases.v` lists the form of each lane in each case.

`Rinv_continuous` in `Recip.v` and `Rdiv_continuous` in `Div.v` show that `1 / r` is continuous at each `r` other than 0, and `r / t` at each `(r, t)` with `t` other than 0. The strongest decoration is `trv` if an argument is empty, or if 0 is in `x` for `recip` or in `y` for `/`, as `def` asks for a nonempty subset of the domain. Otherwise it is `com` if the arguments are bounded and the result is common, and `dac` if not. `DecInterval::recip` passes `trv` to `set_dec` if `x.contains(0.0)`, and `DecInterval::div` if `y.contains(0.0)`, which holds exactly when 0 is a real of the interval (`contains_zero` in `DivZero.v`). Otherwise they pass the decoration of `x`, or the minimum of those of `x` and `y`. As for `x * y`, a common result can come from an unbounded argument: `recip([1, +∞])` is `[0, 1]` and `[1, 2] / [1, +∞]` is `[0, 2]`. `set_dec` would keep `com` there if the arguments were `com`, where IEEE 1788 asks for `dac`. So `dec_recip_correct` and `dec_div_correct` have the `com_common` hypothesis.

`mul_rev_to_pair_correct` in [`MulRev.v`](theories/MulRev.v) shows that `Interval::mul_rev_to_pair`, IEEE 1788's two-output division `mulRevToPair`, returns the intervals that its doc comment describes, and `dec_mul_rev_to_pair_correct` that `DecInterval::mul_rev_to_pair` decorates them as its doc comment says. `mul_rev_one_component` in [`MulRevSets.v`](theories/MulRevSets.v) proves the table of the number of components in the doc comment:

```coq
Theorem mul_rev_to_pair_correct :
  forall has_fma x y, valid x -> valid y ->
  exists u v, Interval.mul_rev_to_pair has_fma x y = Some (u, v) /\
    two_output (mul_rev x y) u v.

Theorem dec_mul_rev_to_pair_correct :
  forall has_fma x y, valid (itv x) -> valid (itv y) ->
  exists u v, DecInterval.mul_rev_to_pair has_fma x y = Some (u, v) /\
    if DecInterval.is_nai x || DecInterval.is_nai y then
      u = DecInterval.NAI /\ v = DecInterval.NAI
    else
      two_output (mul_rev (itv x) (itv y)) (itv u) (itv v) /\ dec v = Trv /\
      ((exists r, mem r (itv x)) -> (exists r, mem r (itv y)) -> ~ mem 0 (itv x) ->
         DecInterval.div has_fma y x = Some u) /\
      ((forall r, ~ mem r (itv x)) \/ (forall r, ~ mem r (itv y)) \/ mem 0 (itv x) ->
         dec u = Trv).

Theorem mul_rev_one_component :
  forall x y, valid x -> valid y -> (exists r, mem r x) -> (exists r, mem r y) ->
  mem 0 y \/ ~ mem 0 x ->
  exists k, component (mul_rev x y) k /\
    forall k', component (mul_rev x y) k' -> forall r, k' r <-> k r.
```

`x` is `self` and `y` is `numerator`, in the order of the Rust arguments. `mul_rev x y` in `Ieee1788.v` is the set `numerator ⊘′ self` of the doc comment, the reals `z` with `t * z` in `y` for some `t` in `x`. Unlike the image of `/`, it holds every real if 0 is in both `x` and `y`, as `t` may be 0. `two_output s u v` states the three cases of the doc comment: if `s` is empty, `u` and `v` are `EMPTY`; if `s` has one component `k`, `u` is the tightest interval that contains `k`, and `v` is `EMPTY`; if `s` has two components `k1` and `k2`, every element of `k1` below every element of `k2`, `u` and `v` are the tightest intervals that contain `k1` and `k2`. `component s k` says that `k` is a connected component of `s`: a nonempty convex subset of `s` that every convex subset of `s` that contains it equals, as the connected subsets of R are the convex ones. "One component `k`" is stated as "every component has the elements of `k`", and "two components" as "every component has the elements of `k1` or of `k2`", so `two_output` also shows that `s` has no more than two. `mul_rev_one_component` gives the cells of the table with one component: for nonempty `x` and `y`, the set has one component if 0 is in `y` or not in `x`. The other cell, 0 in `x` and not in `y`, with 0, 1 or 2 components, says nothing that `two_output` does not. `has_fma` and `Some` are as in `div_correct`.

`Interval::mul_rev_to_pair` matches on `numerator.classify2(self)`, the classes of `y` and `x` in that order, and `mul_rev_to_pair_correct` splits on the 49 pairs:

- The 15 pairs with an empty argument, or with `x` in `Z` and `y` in `N1` or `P1`, give `[EMPTY, EMPTY]` (`mul_rev_empty` in [`MulRevCases.v`](theories/MulRevCases.v)). The set is empty: for `x = [0, 0]`, `t * z` is 0, which is not in such a `y`.
- The 16 pairs with `x` and `y` both in `M`, `N0`, `P0` or `Z` give `[ENTIRE, EMPTY]` (`mul_rev_entire`), as 0 is in `x` and `0 * z = 0` is in `y` for every `z`.
- The 16 pairs with `x` in `N1` or `P1` and a nonempty `y`, or with `x` in `N0` or `P0` and `y` in `N1` or `P1`, give `[y / x, EMPTY]` (`mul_rev_nz`): each calls the same helper as `Interval::div`, or returns `Interval::zero()` as it does (`mul_rev_div_eq`). 0 is not in `x` or not in `y`, so `t` is not 0, and the set is the image of `y × x` under `/` (`mul_rev_div` in `MulRevSets.v`), which `div_correct` encloses tightly. The reals of `x` are all at least 0 or all at most 0, so the set is convex (`mul_rev_convex`), and as it is nonempty, it is its only component.
- The 2 pairs `N1 × M` and `P1 × M` give two components, one on each side of 0, which is not in the set, as `t * 0 = 0` is not in `y` (`mul_rev_N1M` and `mul_rev_P1M` in [`MulRevTwo.v`](theories/MulRevTwo.v)).

`mul_rev_split` in `MulRevSets.v` writes the set with the sets of `DivSets.v`: its elements with `t > 0` are `quot (Up y) (Qp x)`, the quotients of the reals of `y` by the reals of `x` above 0, as `z = (t * z) / t`, and those with `t < 0` are `quot (Um y) (Qn x)`, the quotients of the negated reals of `y` by the negated reals of `x` above 0, as `z = (-(t * z)) / (-t)`. `quot_convex` shows that a set of quotients of a convex set by a convex set of reals above 0 is convex. For `y = [a, b]` and `x = [c, d]` with `c < 0 < d`, stored as `[-a; b]` and `[-c; d]`:

- `N1 × M`, `b < 0`: the reals below 0 are `quot (Up y) (Qp x)`, i.e. `(-∞, b / d]`, or `(-∞, 0)` if `d` is +∞, and those above 0 are `quot (Um y) (Qn x)`, i.e. `[b / c, +∞)`, or `(0, +∞)` if `c` is -∞. `Interval::mul_rev_to_pair` divides `[b; b]` by `[-c; d]` with one `div_ru`, and returns `[+∞; RU(b / d)]` and `[RU(b / (-c)); +∞]`.
- `P1 × M`, `0 < a`: the reals below 0 are `quot (Um y) (Qn x)`, i.e. `(-∞, a / c]`, or `(-∞, 0)` if `c` is -∞, and those above 0 are `quot (Up y) (Qp x)`, i.e. `[a / d, +∞)`, or `(0, +∞)` if `d` is +∞. It divides `[-a; -a]` by `[-c; d]`, and returns `[+∞; RU((-a) / (-c))]` and `[RU((-a) / d); +∞]`.

`two_output_two` in `MulRevSets.v` shows that two nonempty convex sets whose union is the set, with a real between them that is not in it, here 0, are its two components. Each lane is one of the forms of `DivLane.v`: +∞ is form (b) (`div_lane_inf`), as the numerators there, `Um y` for `N1` and `Up y` for `P1`, are above 0, and the reals of an `x` in `M` above 0, and the negations of those below 0, come as close to 0 as asked (`yset_M`), and the other lanes are form (c) (`div_lane_nonpos`), with the largest numerator, `b` for `N1` or `-a` for `P1`, at most 0 and in a lane of `y`, and the largest denominator, `d` or `-c`, or +∞, in a lane of `x`.

`DecInterval::mul_rev_to_pair` returns `[NAI, NAI]` if an argument is NaI. Otherwise its intervals are those of `Interval::mul_rev_to_pair`, as `set_dec` keeps a `valid` interval for a decoration other than `ill`, and the second is decorated `trv`. The doc comment says that if `0 ∉ self ≠ ∅` and `numerator ≠ ∅`, the first output is the same as `numerator / self`, decorated the same way, and `dec_mul_rev_to_pair_correct` states this as an equality with the model of the decorated `/`: `DecInterval.div has_fma y x = Some u`. Such an `x` is in `N1` or `P1`, so `Interval::mul_rev_to_pair` returns `[y / x, EMPTY]`, and both functions pass the minimum of the decorations of `x` and `y` to `set_dec`, which does not depend on their order (`dec_min_comm` in `MulRev.v`). The second output is then `DecInterval::EMPTY`, as the doc comment says, though no theorem states it on its own: the set has one component (`mul_rev_one_component`), so of the three forms of `two_output` only those with the second interval `EMPTY` can hold, and the second output is decorated `trv`. Otherwise the first output is decorated `trv`: if an argument is empty, the set is empty, so the first output is `EMPTY`, which `set_dec` decorates `trv`, and if 0 is in `x`, `x.contains(0.0)` holds (`contains_zero`), and `trv` is what is passed to `set_dec`. The equality needs no `com_common` hypothesis. That the first output then has the decoration that IEEE 1788 asks of `numerator / self` is `dec_div_correct`, which has the hypothesis for both arguments, and `ComCommon.v` proves it for every `DecInterval` that the library makes. `Ieee1788.v` defines no decorations for `mulRevToPair`, so the decorations are those that the doc comment states.

`cancel_minus_correct` in [`Cancel.v`](theories/Cancel.v) shows that `Interval::cancel_minus` returns what its doc comment says: the tightest interval `z` such that `rhs + z ⊇ self` if IEEE 1788's cancelMinus has a value, and `ENTIRE` otherwise. `cancel_plus_correct` shows the same for `Interval::cancel_plus`, with the negations of the reals of `rhs` in place of its reals, and `dec_cancel_minus_correct` and `dec_cancel_plus_correct` that the decorated versions return NaI if an argument is NaI, and otherwise that interval decorated `trv`. `cancel_result_empty` and `cancel_result_hull` in [`CancelSpec.v`](theories/CancelSpec.v) show that such a `z` is what IEEE 1788 asks of an interval version of cancelMinus:

```coq
Theorem cancel_minus_correct :
  forall x y, valid x -> valid y ->
  exists z, Interval.cancel_minus x y = Some z /\
    cancel_result (fun r => mem r x) (fun r => mem r y) z.

Theorem cancel_plus_correct :
  forall x y, valid x -> valid y ->
  exists z, Interval.cancel_plus x y = Some z /\
    cancel_result (fun r => mem r x) (fun r => mem (- r) y) z.

Theorem dec_cancel_minus_correct :
  forall x y, valid (itv x) -> valid (itv y) ->
  exists z, DecInterval.cancel_minus x y = Some z /\
    if DecInterval.is_nai x || DecInterval.is_nai y then z = DecInterval.NAI
    else
      cancel_result (fun r => mem r (itv x)) (fun r => mem r (itv y)) (itv z) /\
      dec z = Trv.

Theorem cancel_result_empty :
  forall X Y z, cancel_result X Y z -> (forall r, ~ X r) -> bounded Y ->
  z = Interval.EMPTY.

Theorem cancel_result_hull :
  forall X Y z a b c d, cancel_result X Y z -> a <= b -> c <= d -> d - c <= b - a ->
  (forall r, X r <-> a <= r <= b) -> (forall r, Y r <-> c <= r <= d) ->
  is_tightest (fun r => a - c <= r <= b - d) z.
```

`x` is `self` and `y` is `rhs`, and `dec_cancel_plus_correct` is `dec_cancel_minus_correct` with `cancel_plus` and `mem (- r) (itv y)`. `cancel_result X Y z` in `Ieee1788.v` says two things. If `cancel_defined X Y`, i.e. cancelMinus has a value, which it has for an empty `X` and a bounded `Y`, and for `X = [a, b]` and `Y = [c, d]` with `d - c <= b - a`, then `z` is `valid`, `sum_superset Y z X` holds, i.e. every real of `X` is a real of `Y` plus one of `z`, and every `valid` interval with that property contains `z`. Otherwise `z` is `ENTIRE`. The doc comment's condition, that both arguments are bounded and that the width of `self` is at least that of `rhs`, does not say what the width of an empty interval is. `cancel_defined` follows IEEE 1788 (§10.5.6 and §12.12.5 of the draft P1788/D9.5), which the table in the code comment of `Interval::cancel_minus` agrees with: an empty `self` gives the empty interval if `rhs` is empty or common, and `ENTIRE` if `rhs` is unbounded. `cancel_result_empty` and `cancel_result_hull` give the two values that IEEE 1788 asks for. In the first case it is the empty interval, as every interval has the property, and the empty one is contained in every other. In the second it is the tightest interval that contains `[a - c, b - d]`, as an interval has the property exactly when it contains `[a - c, b - d]` (`superset_iff`). `Some` means that `sub_ru` returns a value and that the `unreachable!()` is not reached.

`Interval::cancel_minus` returns the empty interval if `x` is empty and `y` is empty or common. It returns `ENTIRE` if `x` or `y` is neither empty nor common, so unbounded (`not_common_unbounded` in [`CancelLanes.v`](theories/CancelLanes.v)), or if `x` is common and `y` empty, where cancelMinus has no value (`not_defined` in `CancelSpec.v`). For common `x = [a, b]` and `y = [c, d]`, stored as `[-a; b]` and `[-c; d]`, it computes `z = sub_ru(x, y)`, i.e. `[RU(c - a); RU(b - d)]`, which `sub_lanes_tightest` in [`CancelHull.v`](theories/CancelHull.v) shows to be the tightest interval that contains `[a - c, b - d]` if `d - c <= b - a`. Each lane is the least float or +∞ at or above its difference (`add_lane` in `AddSub.v`), and the first lane is never -∞, as `Bplus mode_UP` of finite floats gives `-f64::MAX` on a negative overflow, so the lower bound is never +∞, as the comment in the `Greater` case says. `cancel_common_eq` in [`CancelWidths.v`](theories/CancelWidths.v) shows that the rest of the function returns `z` if `d - c <= b - a`, and `ENTIRE` otherwise. It compares the widths rounded to nearest, `wx = RN(b - a)` and `wy = RN(d - c)`, which `hadd_rn` computes and which are each finite or +∞ (`width_lane` in `CancelLanes.v`), so `partial_cmp` never returns `None`:

- If both are +∞, both widths are at least `2^1024 - 2^970` (`width_lane`). Every bound is at most `f64::MAX = 2^1024 - 2^971` in magnitude, so every bound is at least `2^970` in magnitude, where halving a float is exact (`halve`). The function halves the four bounds and compares the halved widths, which are at most `f64::MAX`, instead, as halving keeps the order of the widths.
- If the rounded widths differ, they are in the order of the exact widths, as rounding is monotone. A width that rounds to +∞ is at least `2^1024` when rounded without a largest exponent, so above every finite float (`add_inf_ge`).
- If they are equal, and so finite, Fast2Sum [Dekker 1971] (see `Interval::cancel_minus`) on the larger and the smaller of `-a` and `b`, and of `-c` and `d`, halved if both widths were +∞, gives the exact errors `dwx = (b - a) - wx` and `dwy = (d - c) - wy`, of the halved widths if they were halved (`fast_two_sum` in `CancelLanes.v`), and as `wx = wy`, `dwx >= dwy` holds exactly when `d - c <= b - a`. Fast2Sum needs the addend of the larger magnitude first, and as `-a + b >= 0`, the larger of `-a` and `b` is that one (`max_min_lanes`). Flocq proves Fast2Sum without a largest exponent (`Pff2Flocq.Fast2Sum_correct`), and `fast_two_sum` shows that none of its steps overflows: `|hi - RN(hi + lo)| <= |hi|`, and the error is at most `2^971`. Knuth's 2Sum, which the function used before, can overflow when a bound is `f64::MIN` or `f64::MAX`: for `x = y = [f64::MIN, -3 × 2^970]` it gave `ENTIRE` instead of `[0, 0]`.

`Interval::cancel_plus` calls `cancel_minus` with `-y`, whose reals are the negations of those of `y` (`neg_mem` in `Neg.v`), so `cancel_plus_correct` follows from `cancel_minus_correct`, as `cancel_result` depends only on the reals of its sets (`cancel_result_ext` in `CancelSpec.v`). The decorated versions return NaI if an argument is NaI, and otherwise `set_dec` of the result of the bare version and `trv`, which keeps a `valid` interval and decorates it `trv`, as IEEE 1788 asks of a "trivial" decorated version (§11.7.1 of the draft P1788/D9.5). Neither needs the `com_common` hypothesis.

`exp_correct` in [`Elem.v`](theories/Elem.v) shows that `Interval::exp`, which computes its bounds with MPFR, returns the tightest interval that contains the image of its argument under Stdlib's `exp`, and `dec_exp_correct` that `DecInterval::exp` decorates it as IEEE 1788 asks, with the hypothesis `com_common` of `dec_mul_correct`:

```coq
Theorem exp_correct :
  forall emin emax m, range_ok emin emax -> get_d_ok emin emax m -> exp_ok emin emax m ->
  forall x, valid x -> is_tightest (image_dom real_dom exp x) (Interval.exp m x).

Theorem dec_exp_correct :

  let y := DecInterval.exp m x in
  if DecInterval.is_nai x then y = DecInterval.NAI
  else
    is_tightest (image_dom real_dom exp (itv x)) (itv y) /\
```

`Model.v` leaves the MPFR functions that `src/elementary.rs` calls abstract, as the fields of a record `m : mpfr`, and `range_ok`, `get_d_ok` and `exp_ok` in [`Mpfr.v`](theories/Mpfr.v) state what the theorems assume of them and of MPFR's exponent range `emin`, `emax` (see "What is assumed"). Each bound is one call of a function that `mpfr_fn!` defines: it sets an MPFR number of 53 bits to the argument, which holds it exactly, sets it to the MPFR function of it rounded toward -∞ or +∞ to 53 bits, and converts that to an `f64` with `mpfr_get_d`, rounding in the same direction. `mpfr_fn_round` in [`MpfrRound.v`](theories/MpfrRound.v) shows that the two roundings are one rounding to an `f64` in that direction, including overflow and the subnormal range:

```coq
Lemma mpfr_fn_round :
  forall emin emax m rnd r v, range_ok emin emax -> get_d_ok emin emax m ->
  mpfr_round (mpfr_format emin emax) rnd r v ->
  mpfr_round f64_format rnd r (with_val (mpfr_get_d m rnd v)).
```

`mpfr_round F rnd r v` says that `v` is the real `r` rounded in the direction `rnd` to an element of `F`, where `mpfr_format emin emax` is the reals that an MPFR number of 53 bits holds and `f64_format` those that a finite `f64` holds, and a real beyond every element of `F` rounds to an infinity. Every finite `f64` is an MPFR number of 53 bits (`f64_mpfr_format`), as its significand fits in 53 bits and `range_ok` asks for an exponent range that contains that of `f64`, subnormals included. So, toward -∞, no `f64` is above the rounding `y` of `r` to 53 bits and at most `r`, and the largest `f64` at most `y` is the largest at most `r`, which `get_d_ok` says `mpfr_get_d` returns. If MPFR overflows to -∞, no MPFR number, so no `f64`, is at most `r`, and `mpfr_get_d` keeps the infinity. Toward +∞ it is the same the other way round.

`mono_inc_correct` and `dec_mono_inc_correct` in [`MonoInc.v`](theories/MonoInc.v) prove the theorems for the functions that `impl_mono_inc!` defines once, for any `f` that is increasing and continuous on R and computed by an MPFR function as `mpfr_correct` in `Mpfr.v` says. For a nonempty `[a, b]` they return `[f_rd(a), f_ru(b)]`. At a finite bound, that is `f` of it rounded down or up (`mpfr_fn_correct` in `MpfrRound.v`). At -∞, the MPFR function returns the greatest lower bound of `f` rounded down, or -∞ if `f` has no lower bound (`low_end`), and at +∞ the least upper bound rounded up, or +∞ (`high_end`), which follow from the special values in `<f>_ok`. These bounds need not be values of `f`, as `exp([-∞, 0])` is `[0, 1]`, so the lanes are those of least upper bounds (`tightest_lanes_lub` in `DivTight.v`). `asinh`, `atan`, `exp`, `exp10`, `exp2`, `sinh` and `tanh` are instances, with the facts about their point functions in [`ExpReal.v`](theories/ExpReal.v) and [`TrigReal.v`](theories/TrigReal.v). `log_correct` and `dec_log_correct` in [`LogDom.v`](theories/LogDom.v) do the same for `impl_log!`, which defines `ln`, `log10` and `log2`, for an `f` that is increasing and continuous on `(0, +∞)` and has no bound at either end of it (facts in [`LogReal.v`](theories/LogReal.v)). They intersect the argument with `[0, +∞]`, return the empty interval if that holds no real above 0, and otherwise `[f_rd(a), f_ru(b)]`, where MPFR gives -∞ for a zero and +∞ for +∞. `closed_inc_correct` and `dec_closed_inc_correct` in `ClosedDom.v` do the same for `asin` and `acosh`, which intersect the argument with `[-1, 1]` or `[1, +∞]` and return `[f_rd(a), f_ru(b)]` for a nonempty intersection `[a, b]`, and `acos_correct` and `dec_acos_correct` for `acos`, which is decreasing and returns `[acos_rd(b), acos_ru(a)]`. `Interval::atanh` intersects the argument with `[-1, 1]`, as MPFR gives -∞ and +∞ for -1 and 1, and returns the empty interval if the intersection holds no real of `(-1, 1)`. `Interval::cosh` returns `[cosh_rd(b), cosh_ru(a)]` if `b < 0`, `[cosh_rd(a), cosh_ru(b)]` if `a > 0`, and `[1, cosh_ru(max(-a, b))]` otherwise, as `cosh` is even and increasing on `[0, +∞)`, with its least value 1 at 0.

The decorated versions are the two arms of `impl_dec!`. The first passes the decoration of `x` to `set_dec`, and the second, for `acos`, `acosh`, `asin`, `atanh`, `ln`, `log10` and `log2`, the minimum of it and the decoration that `Interval::<f>_impl` returns, which is `com` if `x` is a nonempty subset of the domain, and `trv` otherwise. `elem_dec_correct` and `elem_dec_impl_correct` in [`ElemDec.v`](theories/ElemDec.v) show for both, once, that this is the decoration that IEEE 1788 asks for. The strongest decoration is `trv` if `x` is empty or has a real outside the domain, `com` if `x` is a nonempty, bounded subset of the domain and the result is common, and `dac` otherwise, as each point function is continuous on its domain, relative to it, so that `asin` is continuous at -1 and 1, as IEEE 1788 counts it. `asin`, `acos` and `acosh` test that `x` is a subset of `[-1, 1]` or `[1, +∞]` with `subset`, and `atanh` and the logarithms that it is in `(-1, 1)` or `(0, +∞)` with `interior` of `[-1, 1]` or `[0, +∞]`, which hold exactly when the reals of `x` are reals of the other interval, or each has a neighbourhood in it (`subset_mem` and `interior_mem` in [`Interior.v`](theories/Interior.v)). `set_dec` lowers `com` to `dac` for a result that is not common, so the only case left is a `com` `x` that is unbounded and gives a common result. `com_common` rules it out for `atan`, `exp`, `exp10`, `exp2` and `tanh`, whose results can be common for an unbounded `x`, such as `exp([-∞, 0]) = [0, 1]`. For the others it cannot happen. `sinh` and `asinh` have no bound at either end, and `cosh` gives +∞ for either infinity, so an unbounded `x` gives an unbounded result. The second arm passes `com` on only for an `x` in the domain, which is bounded for `asin`, `acos` and `atanh`, and which, if it is unbounded, has the upper bound +∞ for the logarithms and `acosh`, which they take to +∞.

`cos_correct` in [`Cos.v`](theories/Cos.v) shows that `Interval::cos`, which computes its bounds with MPFR, returns the tightest interval that contains the image of its argument under Stdlib's `cos`, and `dec_cos_correct` that `DecInterval::cos` decorates it as IEEE 1788 asks, with the hypothesis `com_common`. `cos_encloses` states only that the result contains the image, which is all that `cos_valid` in `ValidElem.v` needs. All three assume `sin_ok` as well as `cos_ok`, as `Interval::cos` calls `sin_rd` and `cos_ru` where it reduces the argument exactly (below):

```coq
Theorem cos_encloses :
  forall emin emax m has_fma first x,
  range_ok emin emax -> get_d_ok emin emax m -> cos_ok emin emax m -> sin_ok emin emax m ->
  valid x ->
  exists y, Interval.cos m has_fma first x = Some y /\
    encloses (image_dom real_dom cos x) y.

Theorem cos_correct :
  forall emin emax m has_fma first x,
  range_ok emin emax -> get_d_ok emin emax m -> cos_ok emin emax m -> sin_ok emin emax m ->
  valid x ->
  exists y, Interval.cos m has_fma first x = Some y /\
    is_tightest (image_dom real_dom cos x) y.

Theorem dec_cos_correct :
  forall emin emax m has_fma first x,
  range_ok emin emax -> get_d_ok emin emax m -> cos_ok emin emax m -> sin_ok emin emax m ->

  exists y, DecInterval.cos m has_fma first x = Some y /\

    else

```

`encloses s y` in `Ieee1788.v` says that `y` is `valid` and contains `s`, the accuracy that IEEE 1788 calls valid. `sin_encloses`, `sin_correct` and `dec_sin_correct` in [`Sin.v`](theories/Sin.v) state the same for `sin`, with the hypotheses `sin_ok` and then `cos_ok`. `tan_encloses`, `tan_correct` and `dec_tan_correct` in [`Tan.v`](theories/Tan.v) state it for `tan` on its domain `tan_dom`, with `tan_ok`, `sin_ok` and `cos_ok`. `Interval::tan` calls neither `f64::max` nor `f64::min`, so it takes no `first`, and `dec_tan_correct` needs no `com_common`:

```coq
Theorem dec_tan_correct :
  forall emin emax m has_fma x,
  range_ok emin emax -> get_d_ok emin emax m -> tan_ok emin emax m ->
  sin_ok emin emax m -> cos_ok emin emax m -> valid (itv x) ->
  exists y, DecInterval.tan m has_fma x = Some y /\
    if DecInterval.is_nai x then y = DecInterval.NAI

      is_tightest (image_dom tan_dom tan (itv x)) (itv y) /\

```

`Interval::cos` of a nonempty `x = [a, b]` computes `q = floor(x / PI)` with the `/` and `floor` of intervals proved above, and reads its bounds `qa` and `qb`; `sin` and `tan` divide by `FRAC_PI_2` instead. `PI_bounds` in [`PiBounds.v`](theories/PiBounds.v) shows that the bounds of `Interval::PI` are below and above π, from Machin's formula and the bounds of the partial sums of its series in Stdlib (`PI_2_3_7_ineq` in `Machin.v`), which `vm_compute` compares with the bounds of `Interval::PI` in `Q`, and the bounds of `Interval::FRAC_PI_2` are those halved. For an interval `C` of finite floats `[lo, hi]` with `1 <= lo < c < hi` (`trig_const`), `trig_reduce` in [`TrigReduce.v`](theories/TrigReduce.v) shows that an infinite bound of `x` gives an infinite bound of `q`, a finite `a` gives an integer `qa` with `qa * c <= a`, strictly unless `qa` is 0, and a finite `b` an integer `qb` with `b < (qb + 1) * c`, so that every real of `x` is in `[qa * c, (qb + 1) * c)`. It uses `trig_quot_lo` and `trig_quot_hi` in [`TrigQuot.v`](theories/TrigQuot.v), which bound the tightest quotient `x / C` below by `a / t` for `t` = `c`, `lo` and `hi`, and above by `b / c`. `n = qb - qa` is rounded to nearest, but the tests `n == 0.0`, `n <= 1.0`, `n < 2.0` and so on decide the exact difference, as rounding to nearest is monotone and the integers that `n` is compared with are floats (`n_small`), and `n` is +∞ if a bound of `x` is infinite (`n_inf`). If `a == b`, `n` is 0 instead. `rem_euclid_2(qa)` and `qa.rem_euclid(4.0)` give the remainders of `qa` by 2 and 4 (`rem_euclid_2_int` and `rem_euclid_4_int`).

Each branch returns one of six forms: `[f_rd(a), f_ru(b)]`, where `f` increases, `[f_rd(b), f_ru(a)]`, where it decreases, `[min(f_rd(a), f_rd(b)), 1]` around a maximum, `[-1, max(f_ru(a), f_ru(b))]` around a minimum, `[-1, 1]` and `[-∞, +∞]`. [`TrigBranch.v`](theories/TrigBranch.v) proves once, for any `f`, when each form contains the image and when it is the tightest interval that does. `cos` is monotone on each `[k * π, (k + 1) * π]`, `sin` on each `[k * π/2, (k + 1) * π/2]`, and `tan` increases between two of its poles, the odd multiples of π/2 ([`TrigPieces.v`](theories/TrigPieces.v)). Every branch contains the image, as the pieces that meet `[qa * c, (qb + 1) * c)` are the ones that the branch's form allows for. When `tan` returns `com` for an `x` with `a != b`, `x` holds no pole: `b < (qb + 1) * π/2` keeps out the pole above it if `qb` is even, `qa * π/2 < a` the pole `qa * π/2` if `qa` is odd, and `cont`, which tests `b` against the lower bound of `qb * FRAC_PI_2` where `n` is the largest that the branch allows, implies that `b` is below `qb * π/2`, a pole, as `qb` is then odd. A singleton `[a, a]` gives `n = 0`, whatever `qa` is, so a monotone form, which is the tightest for one real, for `tan` because `a` is not a pole: `tan_dom_f64` derives this from `pi_irrational` below, as every finite float is rational. An argument at least a period wide gives `[-1, 1]` or `[-∞, +∞]`, which is the tightest, as the argument holds reals where `cos`, or `sin`, is 1 and -1 (`cos_wide`, `sin_wide`), or reals where `tan` is above and below any bound (`tan_wide`). If `qa` and `qb` are the floors `ka` and `kb` of `a / c` and `b / c` (`trig_reduce_exact`), each branch returns the tightest form for `x`.

`x / C` only encloses the quotients `r / c`, as `Interval::PI` and `Interval::FRAC_PI_2` are one ulp wide and the division rounds outward, so `qa` can be below `ka` when `a` is just above a multiple of `c`, and `qb` above `kb` when `b` is just below one. So the three functions keep the `q` and `n` of `qa` and `qb` only in three cases, and otherwise compute them from the quadrants of `a` and `b`, which give the exact floors modulo 4. The first is `n = 0`: either `a == b`, where a monotone form is the tightest whatever `qa` is (above), or `qa = qb`, so that `qa = ka = kb = qb`, as `qa <= ka <= kb <= qb`. The second is `b - a`, rounded to nearest, at least 8, which it is for an unbounded `x` too, as it is then +∞: `x` then holds two reals at least `2 * π` apart (`trig_wide` in [`TrigCert.v`](theories/TrigCert.v)). For `tan`, it is `b - a` at least 4, where `x` is unbounded or more than `π` wide (`tn_sub_wide` in `Tan.v`). The third is that `floors_exact` says that the floors are exact: it divides the singletons `[a, a]` and `[b, b]` by `C`, and tests that the floor of the upper bound of the first quotient is `qa` and that of the lower bound of the second is `qb`. `floors_exact_ok` shows that `a < (qa + 1) * c` and `qb * c <= b` then, as the first quotient contains `a / c` and the second `b / c`, which with `trig_reduce` makes `qa` and `qb` the floors of `a / c` and `b / c`. Otherwise, `quadrant` returns `k mod 4` for the floor `k` of `r / (π/2)`, for a finite float `r`, from the signs of `sin_rd(r)` and `cos_ru(r)` (`quadrant_correct` in [`TrigQuad.v`](theories/TrigQuad.v)). Rounding down keeps `sin r < 0` and never makes a `sin r >= 0` negative, and rounding up keeps `cos r > 0` and never makes a `cos r <= 0` positive, so the tests decide the signs of `sin r` and `cos r` exactly, however close `r` is to a multiple of π/2. On `[k * π/2, (k + 1) * π/2)`, these signs give `k mod 4`, except at the lower end for `k mod 4` = 2 or 3, where `sin r` or `cos r` is 0: an odd multiple of π, or of π/2, which no float is, as π is irrational (`qd_not_kpi` in `TrigQuad.v`, and `tan_dom_f64`). `quadrants(a, b)` returns the quadrant of `a` and a count `n` that is `kb - ka` if that is less than 4, and at least 4 otherwise, for the floors `ka` and `kb` of `a / (π/2)` and `b / (π/2)` (`quadrants_correct` in [`TrigCount.v`](theories/TrigCount.v)). The quadrants give `d = (kb - ka) mod 4`, so `kb - ka` is `d`, where `b - a < (d + 1) * π/2`, or at least `d + 4`, where `b - a > (d + 3) * π/2`. The float `2 * d + 3` lies between the two, more than 0.4 away from each, so `b - a`, rounded to nearest, is at most `2 * d + 3` in the first case and above it in the second. `int_tests` shows that the tests of the branches on such an `n` are those on the integer that it holds. `sin` takes the quadrant of `a` as `q`, `tan` its remainder by 2, with `cont` false, which it is for exact floors in the branches that read it, and `cos`, for the quadrant `j` of `a`, `q = floor(j / 2)` and `n = floor((j % 2 + n) / 2)`, as `floor(r / π) = floor(floor(r / (π/2)) / 2)`. `quadrant` calls `sin_rd` and `cos_ru`, so the theorems about `cos`, `sin` and `tan` assume both `sin_ok` and `cos_ok`. They need no hypothesis about MPFR that `Mpfr.v` did not already state, and no bound on how close a float can be to a multiple of π/2.

`DecInterval::cos` and `DecInterval::sin` pass the decoration of `x` to `set_dec`, as the first arm of `impl_dec!` does. `cos` and `sin` are defined and continuous everywhere, and their results are bounded, so `trig_set_dec_correct` in `TrigBranch.v`, which does for an enclosure what `elem_set_dec_correct` does for a tightest interval, gives the strongest decoration for every `x` that `com_common` allows. `DecInterval::tan` passes the minimum of it and the decoration that `Interval::tan_impl` returns, `com` for an `x` that `tan_impl` finds to lie between two poles and `trv` otherwise, which holds, as `tan` is continuous on its domain, relative to it. It is the strongest, as `[-∞, +∞]` is returned, decorated `trv`, only for an `x` that holds a pole. `tan_impl` returns `com` only for a bounded `x`, so `com_common` is not needed. `Interval::cos` and `Interval::sin` call `f64::max` or `f64::min` at most once on each path, so the theorems hold for every value of `first`, as for `cosh`.

`pi_irrational` in [`PiIrrational.v`](theories/PiIrrational.v) shows that π is irrational, which Stdlib does not prove:

```coq
Theorem pi_irrational : forall p q : Z, (0 < q)%Z -> PI <> IZR p / IZR q.
```

The proof is Niven's (I. Niven, "A simple proof that π is irrational", Bull. Amer. Math. Soc. 53 (1947), p. 509), with the mean value theorem in place of his integral, so that it needs no integrals. If `PI = a / b` with `b > 0`, the polynomial `f(x) = x^n (a - b x)^n` is symmetric about π/2, as `x (a - b x) = b x (π - x)`, so its `k`-th derivative at π is `(-1)^k` times that at 0, which is `n!` times an integer (`nv_d_sym` and `nv_d_int` in [`NivenSym.v`](theories/NivenSym.v)). With `F = f - f'' + f'''' - ...`, the alternating sum of its even derivatives up to the order `2 n`, and `G(x) = F'(x) sin x - F(x) cos x`, `G' = f sin` (`nv_G_deriv`), as `F'' + F = f`, the derivative of order `2 n + 2` being 0 (`nv_d_high`). `G(π) - G(0) = F(π) + F(0) = 2 F(0)` (`nv_G_ends`), which is `2 n!` times an integer. By the mean value theorem (Stdlib's `MVT_cor2`), it is also `π f(c) sin c` for some `c` in `(0, π)`, which is above 0 and at most `π (π a)^n`, as `0 < c (a - b c) < π a` and `0 < sin c <= 1` there. So the integer is at least 1, and `2 n! <= π (π a)^n` for every `n` (`nv_bound`), which fails for large `n`, as `(π a)^n / n!` tends to 0 (Stdlib's `cv_speed_pow_fact`).

`pow_correct` in [`Pow.v`](theories/Pow.v) shows that `Interval::pow`, which computes its bounds with MPFR, returns the tightest interval that contains the image of the box `x × y` under IEEE 1788's `pow`, and `dec_pow_correct` that `DecInterval::pow` decorates it as IEEE 1788 asks, with the hypothesis `com_common` for both arguments. `powi_correct` and `dec_powi_correct` in [`Powi.v`](theories/Powi.v) state the same for `Interval::powi` and `DecInterval::powi`, which are IEEE 1788's `pown`, with `com_common` only for an exponent that is not above 0:

```coq
Theorem pow_correct :
  forall emin emax m first_min first_max x y,
  range_ok emin emax -> get_d_ok emin emax m -> pow_ok emin emax m ->
  valid x -> valid y ->
  is_tightest (image2_set pow_dom Rpow x y) (Interval.pow m first_min first_max x y).

Theorem dec_pow_correct :
  forall emin emax m first_min first_max x y,
  range_ok emin emax -> get_d_ok emin emax m -> pow_ok emin emax m ->
  valid (itv x) -> valid (itv y) -> com_common x -> com_common y ->
  let z := DecInterval.pow m first_min first_max x y in
  if DecInterval.is_nai x || DecInterval.is_nai y then z = DecInterval.NAI
  else
    is_tightest (image2_set pow_dom Rpow (itv x) (itv y)) (itv z) /\
    exists d, strongest2_set pow_dom d Rpow (itv x) (itv y) (itv z) /\
      dec z = dec_min d (dec_min (dec x) (dec y)).

Theorem powi_correct :
  forall emin emax m n x,
  range_ok emin emax -> get_d_ok emin emax m -> pown_ok emin emax m -> is_i32 n ->
  valid x ->
  exists y, Interval.powi m n x = Some y /\
    is_tightest (image_dom (pown_dom n) (fun r => powerRZ r n) x) y.

Theorem dec_powi_correct :
  forall emin emax m n x,
  range_ok emin emax -> get_d_ok emin emax m -> pown_ok emin emax m -> is_i32 n ->
  valid (itv x) -> (0 < n)%Z \/ com_common x ->
  exists y, DecInterval.powi m n x = Some y /\
    if DecInterval.is_nai x then y = DecInterval.NAI
    else
      is_tightest (image_dom (pown_dom n) (fun r => powerRZ r n) (itv x)) (itv y) /\
      exists d, strongest_dom (pown_dom n) d (fun r => powerRZ r n) (itv x) (itv y) /\
        dec y = dec_min d (dec x).
```

For `pow`, `x` is `self` and `y` is `rhs`. `Rpow r t` in `Elementary.v` is `exp(t ln r)`, Stdlib's `Rpower r t`, for `r > 0`, and 0 for `r = 0`, and its domain `pow_dom` holds the points `(r, t)` with `r > 0`, and those with `r = 0` and `t > 0`, as in Table 9.1 of the draft P1788/D9.5. That domain is not a product of two sets of reals, so the image and the decorations are `image2_set`, `p2_set` and `strongest2_set` of `Ieee1788.v`, which take any set of points of R² as the domain (see "What is assumed"). `pow_ok` in `Mpfr.v` is what the theorems assume of `mpfr_pow`. `first_min` and `first_max` say which zero `f64::min` and `f64::max` in `Interval::pow` return if both of their arguments are zeros, as `first` does for `cosh`, and the theorems hold for all four pairs of values. For `powi`, `x` is `self`, and `rhs` is the integer `n`, which `is_i32 n` says an `i32` holds. The point function is Stdlib's `powerRZ r n`: `r` multiplied by itself `n` times for `n > 0`, 1 for `n = 0`, even at `r = 0`, and `1 / r^(-n)` for `n < 0`, with the domain `pown_dom n`, all of R for `n >= 0` and the reals other than 0 for `n < 0`. Table 9.1 makes `pown(x, p)` a family of functions of one real, one for each integer `p`, so `powi` is stated with `image_dom` and `strongest_dom`, as for `sqrt`. `pown_ok` is what the theorems assume of `mpfr_pow_si`. `Some` means that the `transmute` in `classify`, which `Interval::abs` calls for an even `n`, gets the discriminant of a variant.

`Interval::pow` intersects `x` with `[0, +∞]`, as no point of `pow_dom` has `r < 0`, so the image is that of the box with the intersection in place of `x` (`pw_image_inter` in [`PowCases.v`](theories/PowCases.v)), and returns the empty interval if the intersection or `y` is empty. Otherwise, for the intersection `[a, b]` and `y = [c, d]`, `a` is +0 or above 0, never -0 (`pw_xok_inter`), so `pow_ru(a, c)` is never `pow(-0, c)`, which is -∞ for a negative odd integer `c`. For `r > 0`, `r^t` decreases in `r` if `t <= 0` and increases in `r` if `t > 0`, and it decreases in `t` if `r <= 1` and increases in `t` if `r >= 1` ([`PowReal.v`](theories/PowReal.v)). The code splits on the signs of `c` and `d` and on where `[a, b]` is relative to 1, and in each case the bounds of the image are at the corners of the box that it picks:

- `d <= 0` ([`PowNeg.v`](theories/PowNeg.v)): the domain asks for `r > 0`, so the image is empty if `b` is 0. Otherwise the lower and upper bounds are at `(b, d)` and `(a, c)` if `b < 1`, at `(b, c)` and `(a, d)` if `a > 1`, and at `(b, c)` and `(a, c)` otherwise.
- `c > 0` ([`PowPos.v`](theories/PowPos.v)): every point of the box with `r >= 0` is in the domain. The bounds are at `(a, d)` and `(b, c)` if `b < 1`, at `(a, c)` and `(b, d)` if `a > 1`, and at `(a, d)` and `(b, d)` otherwise. `b` may be -0 here, if `x` is `[.., -0]`, and `pow_ru(-0, c)` is then a zero (`pow_fin` in `PowMpfr.v`).
- `c <= 0 < d` ([`PowMix.v`](theories/PowMix.v)): if `b` is 0, the only points of the domain in the box are `(0, t)` with `t > 0`, where `pow` is 0, and the result is `Interval::zero()`. Otherwise the reals of `[a, b]` at most 1 have their least value at `(a, d)` and their largest at `(a, c)`, and those at least 1 at `(b, c)` and `(b, d)`, so the lower bound is `min(pow_rd(a, d), pow_rd(b, c))` ([`PowMixLo.v`](theories/PowMixLo.v)) and the upper bound `max(pow_ru(a, c), pow_ru(b, d))` ([`PowMixHi.v`](theories/PowMixHi.v)). If `a > 1`, `[a, b]` has no real at most 1, but the two bounds are still those of the image, as the corners for the reals at least 1 give both: `pow_rd(a, d)` is at least 1, so at least `pow_rd(b, c)`, and `pow_ru(a, c)` is at most 1, so at most `pow_ru(b, d)`. The same holds the other way round if `b < 1`.

At a corner with `a = 0` and an exponent at most 0, or with `b = +∞`, `c = -∞` or `d = +∞`, the bound of the image is a limit, or there is none, and `pow_rd` and `pow_ru` give it by the special values that `pow_ok` assumes, such as `pow(+0, t) = +∞` for `t < 0` and `pow(r, +∞) = +0` for `0 < r < 1`. A corner `(0, t)` with a finite `t > 0` is a point of `pow_dom`, where `pow` is 0, which `pow_fin` gives. As for `exp`, these bounds need not be values of `pow`, as `pow([2, +∞], [-1, -1])` is `[0, 0.5]`, so the lanes are those of least upper bounds (`tightest_lanes_lub` in `DivTight.v`), which `pl_lo`, `pl_hi`, `pl_lo_fmin` and `pl_hi_fmax` in [`PowMpfr.v`](theories/PowMpfr.v) give from the corners.

`Interval::powi` splits on the sign and the parity of `n`, with the facts about `powerRZ` in [`PownReal.v`](theories/PownReal.v). For `n < 0`, the image of `[0, 0]` is empty (`pwi_neg_zero`). For an even `n`, `r^n` depends only on `|r|`, so the code takes `abs` of `x` (`abs_correct`), and `r^n` decreases in `|r|` for `n < 0` (`pwi_neg_even`) and increases for `n >= 0` (`pwi_pos_even`). For an odd `n < 0`, an `x` with reals on both sides of 0 gives `ENTIRE`, as `r^n` has no bound on either side of 0 (`pwi_neg_odd_entire`), and otherwise `r^n` decreases on the side of 0 that `x` is on, and the code makes a lower bound 0 into +0 and an upper bound 0 into -0, so that `pown_ru(+0, n)` is +∞ and `pown_rd(-0, n)` is -∞ (`pwi_neg_odd`). For an odd `n > 0`, `r^n` increases on all of R (`pwi_pos_odd`).

`Rpow_continuous` in `PowReal.v` shows that `pow` is continuous at each point of `pow_dom`, relative to it, including the points `(0, t)` with `t > 0`, as IEEE 1788 counts it, and `pown_cont` in `PownReal.v` that `pown(x, n)` is continuous at each point of `pown_dom n`. `elem_dec2_impl_correct` in [`Dom2.v`](theories/Dom2.v) does for `impl_dec2!` what `elem_dec_impl_correct` does for the second arm of `impl_dec!`, for any function of two reals on any domain, and gives `dec_pow_correct`. `DecInterval::pow` passes to `set_dec` the minimum of the decorations of `x` and `y` and of the one that `Interval::pow_impl` returns, which is `trv` if the intersection or `y` is empty, and otherwise `com` if `x` is in the interior of `[0, +∞]`, or, for `c > 0`, a subset of it, and `trv` if not (`pw_dec_cases` in `Pow.v`). The strongest decoration is `trv` if the box is empty or has a point outside `pow_dom`, which, for a nonempty box, is when `x` has a real below 0, or has the real 0 and `y` a real at most 0, `com` if the box is a bounded subset of `pow_dom` and the result is common, and `dac` otherwise. As for `atan`, a common result can come from an unbounded argument: `pow([2, +∞], [-1, -0.5])` is `[0, RU(2^-0.5)]`, and `pow([2, 3], [-∞, -1])` is `[0, 0.5]`. So `dec_pow_correct` has the `com_common` hypothesis for both arguments. `DecInterval::powi` passes to `set_dec` the minimum of the decoration of `x` and of `trv` if `x` is empty, or if `n < 0` and 0 is in `x`, and `com` otherwise, so `dec_powi_correct` follows from `elem_set_dec_correct` in `ElemDec.v`. For `n > 0`, an unbounded `x` gives an unbounded result, but for `n <= 0`, a common result can come from an unbounded `x`: `x^0` is `[1, 1]` for every nonempty `x`, and `[1, +∞]` to the power -2 is `[0, 1]`. So `dec_powi_correct` has the `com_common` hypothesis for `n <= 0`.

`atan2_correct` in [`Atan2.v`](theories/Atan2.v) shows that `Interval::atan2`, which computes its bounds with MPFR, returns the tightest interval that contains the image of the box `y × x` under IEEE 1788's `atan2`, and `dec_atan2_correct` that `DecInterval::atan2` decorates it as IEEE 1788 asks, with the hypothesis `com_common` for both arguments:

```coq
Theorem atan2_correct :
  forall emin emax m y x,
  range_ok emin emax -> get_d_ok emin emax m -> atan2_ok emin emax m ->
  valid y -> valid x ->
  exists z, Interval.atan2 m y x = Some z /\
    is_tightest (image2_set atan2_dom Ratan2 y x) z.

Theorem dec_atan2_correct :
  forall emin emax m y x,
  range_ok emin emax -> get_d_ok emin emax m -> atan2_ok emin emax m ->
  valid (itv y) -> valid (itv x) -> com_common y -> com_common x ->
  exists w, DecInterval.atan2 m y x = Some w /\
    if DecInterval.is_nai y || DecInterval.is_nai x then w = DecInterval.NAI
    else
      is_tightest (image2_set atan2_dom Ratan2 (itv y) (itv x)) (itv w) /\
      exists d, strongest2_set atan2_dom d Ratan2 (itv y) (itv x) (itv w) /\
        dec w = dec_min d (dec_min (dec y) (dec x)).
```

`y` is `self`, the interval of the `y` coordinates, and `x` is `rhs`, that of the `x` coordinates, as in IEEE 1788's `atan2(y, x)`. `Ratan2 r t` in `Elementary.v` is `atan(r / t)` for `t > 0`, that plus π for `t < 0` and `r >= 0`, and minus π for `t < 0` and `r < 0`, and π/2 or -π/2 by the sign of `r` for `t = 0`, which is also the formula of the `mpfr_atan2` entry of the MPFR manual. Its domain `atan2_dom` is R² without `(0, 0)`, as in Table 9.1 of the draft P1788/D9.5, which defines `atan2(y, x)` as the principal value of the argument (polar angle) of `(x, y)`. `Ratan2_range`, `Ratan2_polar` and `Ratan2_polar_unique` in [`AtanReal.v`](theories/AtanReal.v) show that `Ratan2 r t` is that angle: for a point of `atan2_dom`, it is the only `θ` in `(-π, π]` with `t = ρ cos θ` and `r = ρ sin θ`, where `ρ = sqrt(r² + t²)`. `atan2_dom` is not a product, so the theorems are stated with `image2_set` and `strongest2_set`, as for `pow`. `atan2_ok` in `Mpfr.v` is what the theorems assume of `mpfr_atan2`. `Some` means that the `transmute`s in `classify` and `classify2` get the discriminant of a variant.

`Interval::atan2_impl` matches on `x.classify2(y)`, the class of `x` first, and `atan2_correct` applies one lemma to each of the 49 pairs. The image is empty if either side of the box is empty, and for `[0, 0] × [0, 0]`, whose only point is not in the domain (`at2_empty` in [`Atan2Const.v`](theories/Atan2Const.v)). In the 15 other pairs whose box contains `(0, 0)`, and in `N1_M`, `N1_N0` and `N1_Z`, where `x < 0` and 0 is in `y`, so that the box meets the half-line `y = 0`, `x < 0`, the bounds of the image are among 0, ±π/2, π and -π. Each is the value at a point of the box, except -π, which `atan2` approaches just below the half-line (`Ratan2_y_0neg`). The code returns `Interval::zero()`, `Interval::PI`, `Interval::FRAC_PI_2`, `-Interval::FRAC_PI_2`, or an interval whose bounds are 0 or a bound of `Interval::PI` or `Interval::FRAC_PI_2` or its negation, such as `[-PI.sup, PI.sup]` (`at2_full` and the other lemmas of `Atan2Const.v`). `PI_up`, `PI_dn`, `FRAC_PI_2_up` and `FRAC_PI_2_dn` in [`PiTight.v`](theories/PiTight.v) show that the bounds of `Interval::PI` and `Interval::FRAC_PI_2` are the floats next to π and π/2, as their bit patterns differ by one, so that these results are the tightest. In the other 17 pairs, the box lies in a closed quadrant, or in one of the half-planes `x > 0`, `y > 0` and `y < 0`, without `(0, 0)`, and the bounds are `atan2_rd` and `atan2_ru` at the corners of the box that give the greatest lower bound and the least upper bound of the image, by the monotonicity of `atan2` (`Ratan2_dec_x`, `Ratan2_inc_x`, `Ratan2_inc_y`, `Ratan2_dec_y_ge` and `Ratan2_dec_y_lt` in `AtanReal.v`): for `y > 0` it decreases in `x`, for `y < 0` it increases in `x`, for `x > 0` it increases in `y`, and for `x < 0` it decreases in `y` on `y >= 0` and on `y < 0`. The one exception is the upper bound of `N1_P0`, where `x < 0` and `y = [0, d]`, which is `PI.sup`, as the image has its greatest element π, at the points `(0, t)`. [`Atan2Right.v`](theories/Atan2Right.v) proves the cases in the first quadrant and `M_P1` and `P1_M`, [`Atan2Lower.v`](theories/Atan2Lower.v) those in the fourth quadrant and `M_N1`, and [`Atan2Left.v`](theories/Atan2Left.v) those in the second and third quadrants, `N1_P0` among them.

At a corner with an infinity, the bound of the image is a limit, and `atan2_rd` and `atan2_ru` give it by the special values that `atan2_ok` assumes, such as `atan2(y, +∞) = +0` for `y > 0` and `atan2(+∞, x) = π/2` rounded for a finite `x` (`at_val` and `atan2_round` in [`Atan2Mpfr.v`](theories/Atan2Mpfr.v)). These bounds need not be values of `atan2`, as the image of `[1, 2] × [1, +∞]` is `(0, atan(2)]`, so the lanes are those of least upper bounds, which `at_hi_lane` and `at_lo_lane` give from the corners, as `pl_hi` and `pl_lo` do for `pow`. MPFR's `atan2` tells +0 from -0, as C99's does: `atan2(±0, x)` is `±π` for `x < 0`, and `atan2(±0, ±0)` depends on both signs. The code passes neither: a corner with a zero `y` has an `x` above 0 or +∞, where both zeros give 0, a corner with a zero `x` has a `y` other than 0, where MPFR gives `±π/2` by the sign of `y` alone, and no corner has two infinities (`at_args`). For `N1_Z`, where `y` is `[0, 0]` and `x < 0`, the code returns `Interval::PI` without calling MPFR, which would give -π if the bound 0 of `y` is -0.

`Ratan2_cont` in `AtanReal.v` shows that `atan2` is continuous at each point off the closed half-line `y = 0`, `x <= 0`, and `Ratan2_not_cont` that it is not continuous at a point `(0, t)` with `t < 0`, relative to the domain, as it is π there and near -π just below. So a box in the domain can lose `com` to the discontinuity, and not only, as for `pow`, to an unbounded box or result: it is `dac` if it meets the half-line but has no point below it, as `[0, 1] × [-2, -1]` and `[0, 0] × [-2, -1]` do, where the restriction of `atan2` to the box is `atan(y / x) + π`, which is continuous (`Ratan2_cont_upper`), and `def` if the box also has points just below the half-line, as `[-1, 1] × [-2, -1]` has (`Ratan2_not_cont_in2`). `Interval::atan2_impl` returns `trv` for an empty box and for one that contains `(0, 0)`, `dac` for `N1_P0` and `N1_Z`, `def` for `N1_M` and `N1_N0`, and `com` for the boxes off the closed half-line `y = 0`, `x <= 0`. `at2_impl_dec` in `Atan2.v`, from the lemmas of [`Atan2Dec.v`](theories/Atan2Dec.v), shows that each of these is the decoration that `dec_holds` in [`Dec2Set.v`](theories/Dec2Set.v) describes: `trv` if `def` does not hold, `def` if `def` holds and `dac` does not, `dac` if `dac` holds and `atan2` is not continuous relative to the domain at some point of the box, and `com` if it is continuous at each. `elem2_set_dec_correct` in `Dom2.v` covers an `impl_dec2!` whose function returns only `trv` or `com`, so `elem2_set_dec_strongest` in `Dec2Set.v` does the same for one that returns any of the four, and gives `dec_atan2_correct`. As for `atan` and `pow`, a common result can come from an unbounded argument, as for `[1, 2] × [1, +∞]` above, which `atan2_impl` decorates `com`. So `dec_atan2_correct` has the `com_common` hypothesis for both arguments.

`from_dec_ninterval_correct` in [`ParseDec.v`](theories/ParseDec.v) shows that `From<DecNInterval> for DecInterval`, which `FromStr` for `DecInterval` calls, returns the tightest interval that contains the reals that a decorated interval literal denotes, decorated as IEEE 1788's textToInterval asks, and `from_ninterval_correct` that `From<NInterval> for Interval`, which `FromStr` for `Interval` calls, returns that interval, if MPFR does what its manual says:

```coq
Theorem from_dec_ninterval_correct :
  forall m x, parse_ok m -> ninterval_ok (nx x) ->
  let y := DecInterval.from_dec_ninterval m x in
  if dec_eqb (nd x) Ill then y = DecInterval.NAI else
  is_tightest (ninterval_set (nx x)) (itv y) /\
  ((forall r, ~ ninterval_set (nx x) r) -> dec y = Trv) /\
  ((exists r, ninterval_set (nx x) r) ->
   dec y = if dec_eqb (nd x) Com && negb (Interval.is_common_interval (itv y))
           then Dac else nd x).

Theorem from_ninterval_correct :
  forall m x, parse_ok m -> ninterval_ok x ->
  is_tightest (ninterval_set x) (DecInterval.from_ninterval m x).
```

`FromStr` works in two steps. The `nom` grammar of `src/parse.rs`, which is not proved (see "What is not proved yet"), reads the literal and returns its bounds, exact GMP rationals or the infinities, as an `NInterval`, with its decoration as a `DecNInterval` `x`, whose fields are `nx x` and `nd x`. Then `From<DecNInterval>` rounds the lower bound down and the upper bound up to `f64`s with MPFR, and decorates the result with `set_dec`. `ninterval_set x` in `Ieee1788.v` is the set of reals that `x` denotes, those at or above its lower bound and at or below its upper bound, and `ninterval_ok x` in `Model.v` is what the grammar is checked by reading to return: `NInterval::EMPTY`, or bounds in order whose lower bound is not +∞ and whose upper bound is not -∞. Without it, `[q, p]` for two rationals `p < q` between the same two adjacent floats would give a nonempty interval for an empty set. `parse_ok m` in `Mpfr.v` is what the theorems assume of `mpfr_set_q`, `mpfr_subnormalize` and `mpfr_get_d` (see "What is assumed"). For `ill`, the result is NaI. Otherwise it is decorated `trv` if the literal denotes no real, and otherwise with the decoration of the literal, except `dac` in place of `com` if the result is not common. §12.12.7 of the draft P1788/D9.5 and §6.7.5 of the draft P1788.1/D9.8 ask for the decoration of the literal, except `dac` in place of `com` if overflow occurred, "that is, x is bounded and y is unbounded". The grammar gives a literal `com` only if both its bounds are rationals (checked by reading), and `from_dec_ninterval_overflow` shows that for such a literal and a decoration other than `ill`, the result is not common exactly when the conversion of a bound overflowed. `From<DecNInterval>` itself lowers the decoration to `dac` when a bound overflowed, which `set_dec` would do anyway, as an overflowed bound is infinite (`overflow_not_common`). `from_ninterval_new` shows, for any MPFR, that `From<DecNInterval>` of `DecNInterval::new(x)`, which `FromStr` uses for a literal without a decoration, is `DecInterval::new` of the interval that `From<NInterval>` returns, i.e. newDec of it, as §6.7.5 of the draft P1788.1/D9.8 asks of a bare literal.

`rational_to_f64_correct` in [`ParseRound.v`](theories/ParseRound.v) shows that `rational_to_f64` rounds a rational `q` once to an `f64`, toward -∞ for a lower bound (`Inf`) and toward +∞ for an upper bound (`Sup`), and that its flags `inexact` and `overflow` say whether `q` is not a finite `f64` and whether the result is infinite:

```coq
Theorem rational_to_f64_correct :
  forall m q infsup, parse_ok m ->
  mpfr_round f64_format (as_rnd_t infsup) (Q2R q)
    (with_val (f64_f (rational_to_f64 m q infsup))) /\
  (f64_inexact (rational_to_f64 m q infsup) = false <-> f64_format (Q2R q)) /\
  f64_overflow (rational_to_f64 m q infsup) =
    negb (is_finite (f64_f (rational_to_f64 m q infsup))).
```

`rational_to_f64` sets MPFR's exponent range to `[-1073, 1024]`, rounds `q` to an MPFR number of 53 bits with `mpfr_set_q`, rounds that to an integer multiple of `2^-1074` with `mpfr_subnormalize`, which emulates the subnormals of `f64`, as in the example of the MPFR manual that follows the entry of `mpfr_subnormalize`, converts it to an `f64` with `mpfr_get_d`, all in the same direction, and sets the range back. `sub_format_f64` in [`ParseFormat.v`](theories/ParseFormat.v) shows that at this range, the numbers that `mpfr_subnormalize` rounds to are exactly the finite `f64`s. `mpfr_subnormalize` rounds `q` itself, not the number that `mpfr_set_q` returned, given that number and its ternary value, and `mpfr_get_d` returns a finite `f64` as it is, an infinity as it is, and a zero as a zero, so the result is `q` rounded once, with overflow to an infinity. The ternary value that `mpfr_subnormalize` returns compares its result with `q`, so it is 0, and `inexact` false, exactly when `q` is a finite `f64` (`ternary_exact`). `number_to_f64_correct` states the same for `number_to_f64`, which calls `rational_to_f64` for a rational and returns -∞ and +∞ as they are, neither inexact nor overflowed (`number_round` and `number_exact`). `number_neg_correct` shows that `-x` of a `Number`, which the grammar uses for a number with a minus sign, negates the reals that it bounds.

`bounds_tightest` in [`ParseHull.v`](theories/ParseHull.v) shows that `Interval::try_from` of the converted bounds of an `x` with `ninterval_ok x`, or `Interval::EMPTY` where it fails, is the tightest interval that contains `ninterval_set x`, which `ParseDec.v` decorates. `NInterval::EMPTY` has the lower bound +∞, which `try_from` rejects. `try_from_ninterval_exact_correct` in [`ParseExact.v`](theories/ParseExact.v) shows that `Interval::try_from_ninterval_exact`, which `interval_exact!` calls, returns `Ok` exactly when both bounds of the literal are exact, i.e. infinities or rationals that are finite `f64`s, and then the interval whose reals are exactly those that the literal denotes, which is the tightest one, as the doc comment of `interval_exact!` says:

```coq
Theorem try_from_ninterval_exact_correct :
  forall m x, parse_ok m ->
  match Interval.try_from_ninterval_exact m x with
  | Some y =>
      number_exact (ninf x) /\ number_exact (nsup x) /\
```

`Some` is `Ok` and `None` the `Err`. A bound that is not exact gives `Err`, whatever the other bound. Unlike `from_dec_ninterval_correct`, the theorem needs no `ninterval_ok`: exact bounds in the wrong order give `Interval::EMPTY`, which holds no real, as the literal then denotes none.

[`ConstPi.v`](theories/ConstPi.v) proves the theorems for `PI`, `TAU` and `FRAC_PI_2` to `FRAC_PI_8`, [`ConstInv.v`](theories/ConstInv.v) for `FRAC_1_PI`, `FRAC_2_PI`, `FRAC_2_SQRT_PI`, `SQRT_2` and `FRAC_1_SQRT_2`, `ConstLn.v` for `E`, `LN_2` and `LN_10`, and [`ConstLog.v`](theories/ConstLog.v) for `LOG10_2`, `LOG10_E`, `LOG2_10` and `LOG2_E`. `is_tightest` of the set that holds only the value says that the constant is the tightest interval that contains the value, as for the operations above. `def_com!` makes each of these constants of `DecInterval` from the constant of `Interval` with the same name, decorated `com`, so its interval is the same, and the second half of each theorem follows from the first.

Each of these constants of `Interval` is `const_interval!(a, b)` for two finite floats `a` and `b`, where `b` is the float after `a`, Flocq's `Bsucc a`, which `vm_compute` checks from their bit patterns. If the value `c` lies strictly between them, `b` is the least float at or above `c`, and `-a` the least at or above `-c` (`pt_up` and `pt_dn` in `PiTight.v`), so `[a, b]` is the tightest interval that contains `c` (`const_tightest` in [`ConstTight.v`](theories/ConstTight.v), by `tightest_lanes` in `AddSub.v`). `B2Q` gives the value of a float as a rational, so that `const_tightest_Q` reduces `a < c < b` to `a < l` and `u < b` for rationals `l <= c <= u`, which `vm_compute` decides in Stdlib's rationals `Q`. The rational bounds of the values come from:

- π: `PI_Q` in `ConstPi.v` bounds π by two rationals `10^-18` apart, from the partial sums of the series of the Machin-like formula `π/4 = 2 atan(1/3) + atan(1/7)` that `PI_bounds` uses. These rationals multiplied by 2, or divided by 2, 3, 4, 6 or 8, bound the values of `TAU` and `FRAC_PI_2` to `FRAC_PI_8`, and 1 and 2 divided by them those of `FRAC_1_PI` and `FRAC_2_PI`.
- The square roots: `const_tightest_sqrt` in `ConstInv.v` compares the squares of the bounds, which are rationals, instead: `a < √2 < b` if `a² < 2 < b²`, `a < 1/√2 < b` if `2a² < 1 < 2b²`, and `a < 2/√π < b` if `a² π_hi < 4 < b² π_lo`, for positive `a` and `b` and the rational bounds `π_lo` and `π_hi` of π.
- e: `exp_Q_bounds` in [`ExpSeries.v`](theories/ExpSeries.v) bounds `exp q` for a rational `0 <= q <= 1` by the reciprocals of two partial sums of the alternating series of `exp(-q)`, which bound it below and above (Stdlib's `alternated_series_ineq`). `es_sumQ` computes these sums in `Q` with the common denominator `d^n n!` of a rational `q = p / d`, so that `vm_compute` adds them without reducing fractions.
- ln 2 and ln 10: `q < ln y` if `exp q < y`, and `ln y < q` if `0 < y < exp q`, so these bounds of `exp` bound `ln 2` by two rationals `10^-24` apart (`LN_2_Q`). The bounds of `ln 10` are above 1, where `exp_Q_bounds` does not apply, so `LN_10_Q` bounds `exp` at a third of each and cubes it, as `exp(3q) = exp(q)³`.
- The logarithms to the bases 2 and 10: `Rlog b r` is `ln r / ln b`, and `ln (exp 1) = 1`, so the values of `LOG10_2`, `LOG10_E`, `LOG2_10` and `LOG2_E` are `ln 2 / ln 10`, `1 / ln 10`, `ln 10 / ln 2` and `1 / ln 2`, which quotients of the rational bounds of `ln 2` and `ln 10` bound.

[`Valid.v`](theories/Valid.v) shows that the hypothesis `valid` of the theorems above holds for every interval that is made by the library's constructors, or computed from such intervals by the operations proved here, any number of times:

```coq
Theorem made_valid :
  (forall x, made x -> valid x) /\ (forall d, dmade d -> valid (itv d)).
```

`made` and `dmade` are inductive predicates on `Interval` and `DecInterval`. Each of their constructors is a place in the library that makes a value other than by an operation, or a proved operation, whose arguments must be `made` or `dmade`. The places that make an `Interval` are `EMPTY`, `const_interval!`, which `ENTIRE` and the other constants of `Interval` are, `zero()`, `TryFrom<(f64, f64)>`, `try_from_be_bytes` and its siblings, `try_from_ninterval_exact`, which `interval_exact!` calls, and the interval of a `dmade` decorated interval, which `DecInterval::interval` and `From<NInterval>`, which `FromStr` calls, return. Those that make a `DecInterval` are the constants `EMPTY`, `NAI` and `ENTIRE`, those that `def_com!` makes, `const_dec_interval!`, `new`, `set_dec`, `TryFrom<(f64, f64)>`, `try_from_be_bytes` and its siblings, and `From<DecNInterval>`, which `FromStr` calls. The operations are those above, on `Interval` and on `DecInterval`, and `convex_hull` and `intersection`. A model that returns an `option`, such as that of `x + y`, gives a `made` value for each `Some` that it returns, and that of `mul_rev_to_pair` gives two, one for each output (`made_mul_rev_to_pair1` and `made_mul_rev_to_pair2`). The theorems above show that it returns `Some` for `valid` arguments (for `x * y`, `mul_add`, `recip`, `x / y` and `atan2` of decorated intervals, also given `com_common`, which `ComCommon.v` proves for every decorated interval, and for `powi`, given that the exponent is an `i32`), so the value that the Rust function returns is `made`. Each step can take either value of `has_fma` and `has_maximum`, so `made_valid` holds whatever values a target gives them. A step through a function of `src/elementary.rs` takes an MPFR `m` and an exponent range with the properties that its theorems assume, `range_ok`, `get_d_ok` and the function's `<f>_ok`, and for `cos`, `sin` and `tan` both `sin_ok` and `cos_ok`, `cos`, `cosh` and `sin` either value of `first`, `pow` any values of `first_min` and `first_max`, and `powi` an exponent `n` with `is_i32 n`. `try_from_ninterval_exact` and `From<DecNInterval>` take any MPFR `m` and any `NInterval`, as any floats that MPFR returns for the bounds make a `valid` interval. Every other public function of the library that returns an `Interval` or a `DecInterval` returns one that these make: `FromStr` for `DecInterval` calls `From<DecNInterval>`, `FromStr` for `Interval` returns the interval of that, `_try_from_str_exact`, which `interval_exact!` calls, calls `try_from_ninterval_exact`, the operators on references, such as `&x + &y`, return what `x + y` and the others return, and the compound assignments, such as `x += y`, assign it.

The proof is by induction on `made` and `dmade` together, with a theorem for each of their constructors:

- [`ValidMake.v`](theories/ValidMake.v): the places that make a value other than by an operation. `TryFrom<(f64, f64)>`, and `try_from_be_bytes` and its siblings, call `with_infsup_raw` only for bounds `a <= b` where `a` is not +∞ and `b` is not -∞, which is what `valid` asks for. `const_interval!` does not compile unless its bounds pass the same test (`const_interval_ok`). `EMPTY` holds `[NaN; NaN]`, and `zero()` holds `[+0; +0]`, i.e. `[0, 0]`. `try_from_ninterval_exact` returns an `Err`, or `Ok` of what `TryFrom<(f64, f64)>` returns for the floats that `number_to_f64` computes, or of `EMPTY`, and `From<DecNInterval>` returns `set_dec` of one of these. `new` and `set_dec` keep the interval that they get or hold `Interval::EMPTY`, and the other places that make a `DecInterval` hold one of the intervals above.
- [`ValidOps.v`](theories/ValidOps.v): the proved operations on intervals. `is_hull` and `is_tightest`, which the theorems above conclude of the result, include `valid`, so `floor_valid` takes it out of `floor_correct`, and so on. Each output of `two_output`, which `mul_rev_to_pair_correct` concludes, is `EMPTY` or `is_tightest`, so `mul_rev_to_pair_valid` shows that both are `valid`. An interval of which `cancel_result` holds, as `cancel_minus_correct` and `cancel_plus_correct` conclude, is `valid` (`cancel_result_valid` in `CancelSpec.v`), which gives `cancel_minus_valid` and `cancel_plus_valid`.
- [`ValidSetOp.v`](theories/ValidSetOp.v): `convex_hull_valid` and `intersection_valid`. Both return the empty interval, or the other argument for `convex_hull`, if an argument is empty. Otherwise, `convex_hull` of `[a, b]` and `[c, d]` takes `max` of both lanes, `[max(-a, -c); max(b, d)]`, i.e. `[min(a, c), max(b, d)]`, whose bounds are ordered, as `min(a, c) <= a <= b <= max(b, d)`. `intersection` takes `min` of both lanes, `[max(a, c), min(b, d)]`, and returns the empty interval if the lower bound is above the upper one. On lanes that are finite or +∞, `max1` and `min1` are `Rmax` and `Rmin`, with +∞ above every real, and return such a lane (`max1_bound` and `min1_bound` in `MaxMin.v`), so neither result has a lower bound +∞ or an upper bound -∞.
- [`ValidDecOps.v`](theories/ValidDecOps.v): the proved operations on decorated intervals. Each returns an argument, NaI, or `set_dec` of what the operation on their intervals returns (for `mul_rev_to_pair`, of each of the two intervals that it returns), except `convex_hull` and `intersection`, which return NaI or that interval decorated `trv`.
- [`ValidElem.v`](theories/ValidElem.v): the functions of `src/elementary.rs` above, on intervals and on decorated intervals. `acos_valid` takes `valid` out of `acos_correct`, and so on, and `cos_valid`, `sin_valid` and `tan_valid` take it out of `cos_encloses`, `sin_encloses` and `tan_encloses`, as `encloses` includes it too. The decorated versions return `set_dec` of what the function on their intervals returns, with some decoration (`ve_elem_dec_valid` and `ve_elem_dec_impl_valid`, and for `atan2`, `pow` and `powi`, `dec_atan2_valid`, `dec_pow_valid` and `dec_powi_valid` directly), so `dec_acos_valid` and the others follow as in `ValidDecOps.v`, without `com_common`.

## What is assumed

[`Model.v`](theories/Model.v) transcribes the Rust functions line by line. It is the only file that has to be checked against the Rust code by reading, and it has to be updated whenever those functions change. Its modelling choices:

- `f64` is Flocq's binary64, and Rust's `+`, `-` and `/` are Flocq's `Bplus`, `Bminus` and `Bdiv` rounded to nearest, ties to even. `generic.rs` relies on this default rounding mode. `f64::mul_add` is Flocq's `Bfma` in the same mode, with a single rounding, as Rust specifies it whether or not the target has an FMA instruction. `f64::sqrt` is Flocq's `Bsqrt`, also rounded to nearest, ties to even. Flocq has no remainder, so `x % y` of `f64`s is `frem`, C's `fmod`: the exact `x - k * y` for the real quotient `x / y` truncated to an integer `k`, which is always a float, with the sign of `x`. `x.rem_euclid(y)` is `rem_euclid`, the standard library's `let r = x % y; if r < 0.0 { r + y.abs() } else { r }`.
- NaN payloads and signs are not modelled: all NaNs are the same value, so `Bopp` keeps a NaN as it is where Rust's unary `-` flips its sign bit. The functions modelled here only read the exponent field of a NaN, which is all ones for every NaN, except `add_odd`. It reads the lowest bit of `s`, which for a NaN is part of the payload, but returns a NaN for a NaN `s` either way.
- Bit patterns are integers rather than `u64`, so `b + 1` and `b - 1` in `step_up` cannot wrap around. `step_up_no_wrap` in `Encoding.v` shows that for finite floats they stay in the range of `u64`, so they don't wrap around (or panic) in Rust either. The same holds for ±∞ and NaN, but is not proved: `b + 1` is only computed if `x > 0`, so the sign bit of `b` is clear, and `b - 1` only if `x < 0`, so it is set.
- The other integer types, `u128`, `u64`, `u32` and `i32`, are integers too. `rhs % 2 == 0` of the `i32` `rhs` in `Interval::powi` is `Z.rem n 2 =? 0`, as Rust's `%` of integers truncates the quotient, as `Z.rem` does, and with the divisor 2 it cannot overflow. In the slow path and in `mul1_ru_tiny`, every operation that panics in a debug build returns `None`: one whose result does not fit its type, a shift by a negative amount or by at least the width of the type, and the `debug_assert!`s in `sum_round_up` and `mul1_ru_tiny`. A release build would wrap around instead, so a theorem that a function returns `Some` covers both kinds of build. The integer `/` and `%` in `div1_ru_slow` return `None` for a zero divisor, which panics in both kinds of build. Arithmetic on the fields of a bit pattern, in `exponent` and `decompose`, cannot overflow and is not checked.
- Casts that could change a value reduce it modulo the size of the target type, as Rust does: `(e + 1023) as u64`, `kept as u64` and `(ex - ey) as u32`. Casts that keep the value are left out: those of the 11-bit exponent field in `exponent` and `decompose`, and, each with a comment, the `leading_zeros() as i32` casts, `sh as i32` and the `as u128` casts of significands.
- `kept as f64` is Flocq's `binary_normalize` rounded to nearest, ties to even, like Rust's conversion from `u64`. A float literal is the same conversion of its value: Rust rounds a literal to nearest too, and the ones used, `134217729.0` (`2^27 + 1`) in `split`, `1.0` and `18446744073709551616.0` (`2^64`) in `sqrt1_slow` and `mul1_ru_tiny`, `1.0` in `Interval::sign`, in `Interval::cosh`, in `Interval::pow` and in the domains of `acos`, `acosh`, `asin` and `atanh`, `1.0`, `2.0`, `3.0`, `4.0` and `8.0` in `Interval::cos`, `Interval::sin`, `Interval::tan`, `rem_euclid_2`, `quadrant` and `quadrants`, and `4503599627370496.0` (`2^52`) in `round_ties_even1`, are exact. `-1.0` in `Interval::sign`, in `Interval::recip`, in `Interval::atanh`, in `Interval::cos`, in `Interval::sin` and in the domains of `acos`, `asin` and `atanh` is the negation of the literal `1.0`, and `-0.0` in `Interval::powi` that of `0.0`, as Rust parses them. The bounds of the constants of `Interval` from `E` to `TAU`, decimal literals that Rust rounds to nearest, are given by the bit patterns of the floats they round to, which the test `constants_bits` in `src/constants.rs` checks. [`Mpfr.v`](theories/Mpfr.v) states what the theorems about the functions of `src/elementary.rs` and the conversions of `src/parse.rs` assume of MPFR, and has to be checked by reading against the MPFR manual (of MPFR 4.2.2, which `gmp-mpfr-sys` 1.7.1 bundles), as `Model.v` is against the Rust code. Every hypothesis is an argument of the theorems, not an axiom:

- `range_ok emin emax`: MPFR's exponent range `[emin, emax]` contains `[-1073, 1024]`, so that every finite `f64` is an MPFR number of 53 bits. The range is global state that `src/elementary.rs` does not set. `rational_to_f64` in `src/parse.rs` sets it to `[-1073, 1024]` for one conversion and then sets it back, and that range satisfies `range_ok`, but the hypotheses about its MPFR calls are stated at that range instead (`parse_ok` below). MPFR's default range, `[-(2^30 - 1), 2^30 - 1]` (`MPFR_EMIN_DEFAULT` and `MPFR_EMAX_DEFAULT` in `mpfr.h`), contains it, but a program that narrows the range with `mpfr_set_emin` or `mpfr_set_emax`, for example through `rug`, is not covered.
- `mpfr_format emin emax`: the reals that an MPFR number of 53 bits holds, 0 and `m × 2^e` with a significand `m` of 53 bits, `1/2 <= |m| < 1` and `emin <= e <= emax`, as MPFR has no subnormals (§4.2 "Nomenclature and Types" and `mpfr_get_emin` in §5.13). `f64_format` is the reals of finite `f64`s.
- `mpfr_round F rnd r v`: toward -∞, `v` is the largest element of `F` at or below `r`, or -∞ if there is none, and toward +∞ the least at or above `r`, or +∞. This is §4.4 "Rounding", which rounds toward -∞ to the number closest to `r` at or below it, and toward +∞ at or above it, read with the infinities among the numbers and the exponent range of §4.2, so that it covers overflow and underflow. §4.6 "Exceptions" says when these occur, but gives the result only for an overflow rounded to nearest, so the results toward -∞ and +∞, such as the largest MPFR number for a positive overflow rounded down, are read into §4.4. A result 0 may be a zero of either sign, as the theorems do not use it, and a result other than 0 is an `MNum`.
- `get_d_ok`: `mpfr_get_d` converts an MPFR number of 53 bits other than 0 to the `f64` that rounds it in the direction `rnd`, including overflow and the subnormal range of `f64`, a zero to a zero, and an infinity to the infinity of the same sign (`mpfr_get_d` in §5.4 "Conversion Functions"). The entry says only that it converts "using the rounding mode rnd", so that this rounding is to binary64 with its overflow and its subnormals, as IEEE 754 rounds, is read into it.
- `mpfr_correct emin emax D f g`: for a finite `f64` `x` whose real is in the domain `D`, `g rnd (with_val x)` is `f(x)` rounded in the direction `rnd` to an MPFR number of 53 bits. MPFR rounds every function correctly on its domain (§4.4, and §4.5 "Floating-Point Values on Special Numbers": "When the input point is in the domain of the mathematical function, the result is rounded as described in Rounding"). The entries of the functions in §5.7 "Transcendental Functions" say which mathematical function each computes, and `Elementary.v` defines it.

- `ternary_ok r v t`: the ternary value `t` of an MPFR result `v` for the exact result `r` is 0 if `v` is `r`, positive if `v` is above `r`, and negative if it is below (§4.4 "Rounding", which defines the ternary value). An infinity is above or below every real, so its ternary value is not 0, and no NaN is the result for a real.
- `set_q_ok emin emax m`: `mpfr_set_q` rounds a rational in the direction `rnd` to an MPFR number of 53 bits, as `mpfr_round` says, and returns its ternary value (the entry of `mpfr_set_q` in §5.2 "Assignment Functions", which sets the number "from op, rounded toward the given direction rnd", and §4.4). The entry also says that `mpfr_set_q` converts 0 to +0, which the theorems do not use, and that it "might fail if the numerator (or the denominator) cannot be represented as a mpfr_t", without saying how. `set_q_ok` assumes that it does not fail, and rounds every rational.
- `sub_format emin emax`: the MPFR numbers of 53 bits that are integer multiples of `2^(emin - 1)`. These are the numbers that `mpfr_subnormalize` rounds to: its entry in §5.13 "Exception Related Functions" says that in the subnormal exponent range, from `emin` to `emin + 51` for 53 bits, it rounds to "an integer multiple of 2^(e-1)", where `e` is `emin`, and that outside it, it keeps the number.
- `subnormalize_ok emin emax m`: if `x` is the real `r` rounded in the direction `rnd` to an MPFR number of 53 bits, with the ternary value `t`, `mpfr_subnormalize` returns `r` rounded in the direction `rnd` to `sub_format`, and the ternary value of that against `r`. Its entry says that it rounds `x` "according to rounding mode rnd and previous ternary value t, avoiding double rounding problems", that `rnd` and `t` "must be the rounding mode and the returned ternary value used when computing x", as they are in `rational_to_f64`, and that "the result is compared to the exact one, not the input value x". The example that follows the entry, of how to emulate binary64 arithmetic with MPFR, sets `emin = -1073` and `emax = 1024` and calls `mpfr_subnormalize` with the ternary value of the operation before it, as `rational_to_f64` does.
- `parse_ok m`: `set_q_ok`, `subnormalize_ok` and `get_d_ok` at the range `[-1073, 1024]` that `rational_to_f64` sets. That range is not a hypothesis, as the code sets it, unlike `range_ok` for `src/elementary.rs`, but that it stays set during these calls is assumed (see "What is not proved yet").

[`Elementary.v`](theories/Elementary.v) defines the point functions that are not in Stdlib, by the usual formulas: `Rexp2` and `Rexp10` as `Rpower 2` and `Rpower 10`, `Rlog2` and `Rlog10` as `Rlog 2` and `Rlog 10`, i.e. `ln r / ln 2` and `ln r / ln 10`, `Racosh r` as `ln (r + sqrt (r * r - 1))` and `Ratanh r` as `ln ((1 + r) / (1 - r)) / 2`, and the domains `real_dom`, all of R, `log_dom`, `(0, +∞)`, `asin_dom` and `acos_dom`, `[-1, 1]`, `acosh_dom`, `[1, +∞)`, `atanh_dom`, `(-1, 1)`, and `tan_dom`, R without the odd multiples of π/2, those of Table 9.1 of the draft P1788/D9.5. It defines `Rpow r t`, IEEE 1788's `pow`, as `Rpower r t`, i.e. `exp(t ln r)`, for `r > 0` and 0 otherwise, with the domain `pow_dom` of that table, the points `(r, t)` with `r > 0`, or with `r = 0` and `t > 0`, and the domain `pown_dom n` of `pown(x, n)`, all of R for `n >= 0` and R without 0 for `n < 0`. It defines `Ratan2 r t`, IEEE 1788's `atan2(y, x)` with `r` as `y` and `t` as `x`, by the usual formula: `atan(r / t)` for `t > 0`, that plus π for `t < 0` and `r >= 0`, and minus π for `t < 0` and `r < 0`, and π/2 or -π/2 by the sign of `r` for `t = 0`, with the domain `atan2_dom` of that table, R² without `(0, 0)`. The table defines `atan2(y, x)` as the principal value of the argument of `(x, y)`, and `Ratan2_range`, `Ratan2_polar` and `Ratan2_polar_unique` in `AtanReal.v` show that `Ratan2` is that angle, so the formula can be checked against the table's definition by those lemmas as well as by reading. Stdlib's `exp`, `ln`, `sin`, `cos`, `tan`, `sinh`, `cosh`, `tanh`, `arcsinh`, `atan`, `asin` and `acos` are IEEE 1788's `exp`, `log`, `sin`, `cos`, `tan`, `sinh`, `cosh`, `tanh`, `asinh`, `atan`, `asin` and `acos`, and Stdlib's `powerRZ r n`, as a function of `r`, is IEEE 1788's `pown(x, n)`. Like `Ieee1788.v`, it has to be checked by reading. A function defined only on a domain is a function from R to R, or from R² to R for `pow` and `atan2`, whose values outside the domain the theorems do not use.

[`Ieee1788.v`](theories/Ieee1788.v) states what IEEE Std 1788-2015 asks of an interval version of a function: the hull of the image (`is_hull`), or the tightest interval that contains it (`is_tightest`) where its bounds need not be floats, or an interval that contains it (`encloses`), the accuracy that IEEE 1788 calls valid, which `cos_encloses`, `sin_encloses` and `tan_encloses` state on their own, and the properties of the decorations. It and `Elementary.v` are the only files that have to be checked against the standard by reading, its `two_output` against the doc comment of `Interval::mul_rev_to_pair`, and its `cancel_result` against that of `Interval::cancel_minus`. For `com`, the standard asks for the computed interval to be bounded. `p`, for functions of one real, asks for the image instead. `is_hull_bounded` in `Integer.v` shows that the two are the same for a hull, which each function stated with `p` returns. `p2`, for functions of two reals, asks for the computed interval, as the standard does, as `x + y` can overflow where the image is bounded. Stdlib's `continuity_pt` and `continue_in` are for functions of one real, so for functions of two, `Ieee1788.v` defines continuity on R² itself, by ε and δ with the norm `max(|r|, |t|)` (`continue_in2`, `continuity2_pt`). It also defines the image of a box (`image2`) and the decorations of a function of two reals (`p2`, `strongest2`). For a function of one real that is defined only on a set of reals, its domain, such as `sqrt` on `[0, +∞)` (`sqrt_dom`), it defines the image of the reals of an interval that are in the domain (`image_dom`) and the decorations (`p_dom`, `strongest_dom`). `def`, `dac` and `com` ask for the interval to be a nonempty subset of the domain, and `com` for continuity at each of its points relative to the domain, as IEEE 1788 counts `sqrt` as continuous at 0. For `com`, `p_dom`, like `p2`, asks for the computed interval to be bounded. `sqr` is stated with these too, with the domain `sqr_dom`, which is all of R, because a square can overflow where the image is bounded, and so is `recip`, with the domain `recip_dom`, the reals other than 0. For a function of two reals whose domain is a product `D1 × D2` of two sets of reals, such as `/` on `div_dom1 × div_dom2`, i.e. R × (R ∖ {0}), it defines the image of the points of a box that are in the domain (`image2_dom`) and the decorations (`p2_dom`, `strongest2_dom`), as `image_dom`, `p_dom` and `strongest_dom` do for one real. A box is a nonempty subset of such a domain exactly when each of its sides is a nonempty subset of the matching factor, and `continue_in2` already takes a product of two sets, so `p2_dom` can state continuity relative to the domain as it states continuity relative to a box. A product suffices for `/`. For a function of two reals whose domain is any set `D` of points of R², such as `pow` and `atan2`, whose domains `pow_dom` and `atan2_dom` are not products, it defines the image of the points of a box that are in `D` (`image2_set`), continuity at a point relative to `D` (`continue_in2_set`), and the decorations (`p2_set`, `strongest2_set`), where `dac` asks for the restriction of the function to the box to be continuous, and `com` for continuity at each point of the box relative to `D`, as `p2_dom` does for a product. [`Dom2.v`](theories/Dom2.v) shows that for a product `D1 × D2` these are `image2_dom`, `continue_in2`, `p2_dom` and `strongest2_dom`, and that for all of R² `image2_set`, `p2_set` and `strongest2_set` are `image2`, `p2` and `strongest2`. For a function of three reals that is defined on all of R³, such as `fma`, which is `Rfma`, `r * t + u`, it defines continuity on R³ as on R², with the norm `max(|r|, |t|, |u|)` (`continue_in3`, `continuity3_pt`), the image of a box `x × y × z` (`image3`), and the decorations (`p3`, `strongest3`), where `com`, as in `p2`, asks for the computed interval to be bounded. For two-output division, `mulRevToPair(b, c)`, it defines the set `mul_rev b c` of reals `z` with `t * z` in `c` for some `t` in `b`, the convex sets of reals (`convex`), the connected components of a set of reals, which are its maximal nonempty convex subsets (`component`), and the outputs that the doc comment of `Interval::mul_rev_to_pair` describes for a set (`two_output`): both `EMPTY` for an empty set, the tightest interval that contains its only component and `EMPTY` for a set with one component, and the tightest intervals that contain its two components, the lower one first, for a set with two. For cancellative subtraction, `cancelMinus(x, y)`, it defines, for sets of reals `X` and `Y`, `Y + Z ⊇ X` (`sum_superset`), when cancelMinus has a value (`cancel_defined`): for an empty `X` and a bounded `Y`, and for `X = [a, b]` and `Y = [c, d]` with `d - c <= b - a`, and the result that the doc comment of `Interval::cancel_minus` describes (`cancel_result`): if cancelMinus has a value, the `valid` interval `z` with `Y + z ⊇ X` that every other `valid` interval with this property contains, and `ENTIRE` otherwise. `X` and `Y` are sets rather than intervals so that `cancelPlus(x, y)`, which is `cancelMinus(x, -y)`, is stated with the negations of the reals of `y` rather than with the model of `-y`. For interval literals, it defines the set of reals that an `NInterval` denotes (`ninterval_set`), with `above_num` and `below_num` for the reals at or above a lower bound and at or below an upper bound, where -∞ and +∞ bound nothing on their side and a lower bound +∞ or an upper bound -∞ leaves no real, as in `NInterval::EMPTY`. The theorems state textToInterval's result as the tightest interval that contains that set, the hull that §12.12.7 of the draft P1788/D9.5 asks for in an IEEE 754 binary64 type.

The theorems depend on four axioms. Three come from Stdlib's real numbers: `sig_forall_dec`, `sig_not_dec` and `functional_extensionality_dep`. The fourth is excluded middle (`classic`), which Flocq uses. `make` fails if [`Assumptions.v`](Assumptions.v) finds any other axiom, e.g. a proof left `Admitted`.

## What is not proved yet

- The SIMD backends that vectorize the same algorithm, such as `src/simd/x86_64/lanewise.rs` and `src/simd/wasm32.rs`. If the fast path rejects either lane, `mul_ru` of the `fma`, `sse42` and `wasm32` backends calls `mul_ru_tiny`, which rounds a product below `2^-968` as `mul1_ru_tiny` does, but differs from it in three ways. It computes the fast path's result, the result for a zero `RN(x * y)` and the result through the scaled product in both lanes, and selects one in each lane, where `mul1_ru_tiny` computes only the one that its lane needs. It tells the sign of a zero `RN(x * y)` by comparing its bit pattern with that of +0 as signed integers. And it does not choose the lanes by the exponent of `RN(x * y)`, as `mul1_ru_tiny` does: it accepts a rejected lane if `RN(x * y)` is zero or `two_prod_is_exact` holds for the scaled product, which it checks at run time, and otherwise has the portable backend's `mul_ru` recompute both lanes.

## Building

You need Rocq 9.1, its Stdlib and Flocq 4.2.2. With [opam](https://opam.ocaml.org):

```bash
opam repo add rocq-released https://coq.inria.fr/opam/released
opam install rocq-core.9.1.1 rocq-stdlib.9.0.0 coq-flocq.4.2.2
make -C rocq
```

You can also use Docker, as CI does ([`ci-rocq.yml`](../.github/workflows/ci-rocq.yml)). The container's user (uid 1000) must be able to write to `rocq/`.

```bash
docker run --rm -v "$PWD/rocq:/w" -w /w rocq/rocq-prover:9.1 \
  bash -c 'opam install -y coq-flocq.4.2.2 && make'
```

Warnings are errors. `make clean` removes the build outputs.
